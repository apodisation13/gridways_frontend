# Gridways achievements

Работай в пределах запроса: обсуждение не означает разрешение менять код или БД. Существующая реализация важнее устаревшего примера из чата.

## Контекст по задаче

Начни с [README](../../../docs/achievements/README.md). Затем прочитай только нужное:

- Конфиги/категории: [формат и правила](../../../docs/achievements/configs.md), [валидные примеры](../../../docs/achievements/config-examples.json).
- Новый источник события: [форматы и карта подключений](../../../docs/achievements/events.md).
- Подсчёт, синхронизация, награды: [архитектура и ограничения](../../../docs/achievements/architecture.md).

Сверь затронутые TS-типы/обработчики и backend `user_achievements` до изменения механики. Бэк — отдельный checkout; известные пути в README являются подсказкой. Если его нет, явно обозначь непроверенную часть. Разрешение пользователя на задачу не отменяет файловые ограничения среды.

## Выбор изменения

1. Если существующих event/filters/counter достаточно, выдай только конфиг нужной вложенности. Не расширяй runtime ради нового названия фракции или поля actor. Не импортируй примеры поверх каталога БД.
2. Для нового места вызова используй существующую мастер-функцию после успешной операции. Снимок actor/recipe/before сохраняй до await. В компонентах не проверяй конкретные задания. При замене ResourcesChanged на составное событие убери старый вызов: расходы не должны удвоиться.
3. Для нового wire-события или счётчика согласуй TS enum/input, preview и backend schema/processor. Локальные промежуточные события не уходят в API. Сохраняй терминологию upgrade_type/upgrade_subtype.
4. Не встраивай трекер в обычные resource actions/mutations: компоненты вызывают его явно. Модуль достижений отдельно обрабатывает собственные награды. Не меняй экономику начислений/списаний ради телеметрии.

## Что не потерять

- Подтверждённый прогресс и награды — от бэка; frontend preview не ставит даты и не начисляет ресурсы. current проверяется также при загрузке, но загрузка не является покупкой или заработком.
- Queue в памяти, без wire-ID/ack/dedup и без повторов сетевых ошибок по принятому решению. 401 использует штатный refresh/retry. Не возвращай `_retry: true` в вызов API достижений.
- unique не изменяет confirmed seen по ссылке. Отсутствующий путь не совпадает с null и не проходит ne. Награды считаются по фактически выданным суммам, а не каталогу.
- Не объявляй daily/weekly, серии/сбросы и отложенные интеграции реализованными без кода. Для «каждый» проверяй достижимость полного списка. При изменении смысла старого контракта учитывай сохранённые ID и выданные награды.

## Проверка и сохранение знаний

Из корня фронта проверь готовый каталог:

```sh
python3 docs/achievements/validate_catalog.py path/to/achievements.json
```

Валидатор не подтверждает экономику, наличие всех игровых объектов или совместимость произвольно расширенной схемы. При изменении механик обновляй и его. Для кода используй относящиеся к изменению type/lint проверки и временные проверки поведения. По текущему указанию пользователя backend tests не запускать, если он явно не изменит это указание; frontend tests/ автоматически не создавать.

Проверь риски конкретного изменения: replay без удвоения, пустые/неподходящие события, достижение цели и немедленная отправка, снимки/лимиты, сохранение завершённых задач. Не запускай генерацию сезонов или изменения БД как часть проверки достижений.

После изменения механики/формата/мест подключения обнови соответствующий документ в docs/achievements и пример, если он изменился. Отдели реализованное от предложенного. Сообщи пользователю коротко: что поменялось, нужен ли новый конфиг/бэк, что проверено и что остаётся.
