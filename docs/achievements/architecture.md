# Архитектура достижений

Состояние на 2026-11-13. См. [события и места подключения](events.md), [конфиги](configs.md).

## Разделение ответственности

Компонент сообщает об успешном действии через `trackAchievementEvent`. Он не проверяет конкретные задания. Снимки объектов/баланса сохраняются до операции, трекер вызывается после успешного await. Типы живут в `src/types`, логика — в `src/logic/achievements`.

Трекер нормализует вход, делает JSON-снимок и добавляет события в Vuex. `processAchievementEvents` — чистый предварительный расчёт поверх подтверждённого прогресса. `syncAchievementEvents` выбирает момент отправки, action `sendAchievementEvents` вызывает API и применяет ответ.

Обычные `processResources`, `processCraftMillCard`, `openRelatedLevels`, `postUserUpgrade` не содержат вызовов трекера. Вызовы стоят на страницах/в общем игровом mixin. Исключение по назначению: сам модуль достижений после своего ответа учитывает фактически выданные награды через `trackAchievementRewards`, затем проверяет баланс. Не внедрять проверки контрактов в расчёт начислений/списаний бэка.

## Хранение

`game_constants.data.achievements` содержит `permanent/daily/weekly`. В каждой секции `title`, `categories`; в категории `id/title/ordering/achievements`; внутри последнего — задания по ID. Фронту из GAME_DATA сейчас приходит только `permanent`. Общая функция бэка `get_game_constants` удаляет JSONB-пути daily/weekly при чтении, а не только на HTTP-границе: это нужно учесть при будущей реализации recurring.

`user_achievements`: PK `id = users.id`, `progress JSONB`, timestamps. Загрузка общего прогресса пользователя вызывает get-or-insert и получает `{}` при отсутствии достижений. POST обработки событий сейчас предполагает, что строка уже создана при загрузке.

```json
{
  "permanent": {
    "craft_all_inventory_items": {
      "value": 2,
      "seen": ["shields", "draw_cards"],
      "completed_at": null,
      "reward_granted_at": null
    }
  }
}
```

Отсутствующая запись = нулевой прогресс. ID задания уникален внутри секции даже между категориями; категория в пользовательском прогрессе не хранится. Даты выполнения/выдачи ставит бэк в UTC. `seen` нужен только unique; массив не изменяется по ссылке при локальном replay.

Для будущих daily/weekly согласована форма `{ "period": "…", "tasks": {} }`, но код пока считает только permanent. Таблица `achievement_sets` уже существует: `id`, `period_type`, `period_start`, `task_ids` (JSONB список строк), timestamps; уникальная пара `(period_type, period_start)`. План — хранить историю общих выбранных наборов, а не персональную случайную выдачу.

## Подсчёт

- `count`: +1 за подходящее событие.
- `sum`: положительное конечное число из `counter.field`.
- `unique`: строка или конечное число из `counter.field`, добавляем в `seen` только новое, `value = len(seen)`. Число 1 и строка "1" различаются. null, bool, объект, массив и отсутствующее поле не учитываются.
- `current`: заменяем value текущим числом; пока нет подтверждения, он может уменьшаться. Только для `resources.checked` / `upgrades.checked`. Нулевое значение допустимо.

Значение ограничено target; подтверждённые награды повторно не выдаются. Фронт не создаёт даты выполнения и не начисляет ресурсы самостоятельно. Порог локально достигнут — это ещё не подтверждённый контракт.

`localUserAchievements` для UI = подтверждённый прогресс + replay in-flight/pending событий + живые снимки ресурсов/прокачек. Локально собранный unique не должен портить исходный `seen`. После ответа/ошибки preview пересчитывается.

## Очередь и HTTP

```json
{"events":[{"type":"resource.gained","data":{"resources":{"money":100}}}]}
```

POST `/user-achievements/{user_id}`. Локальный UUID есть у `AchievementEvent`, но в запрос не входит. Нет acknowledged_event_ids, таблицы дедупликации, localStorage/outbox и гарантии доставки. Это осознанный компромисс первой версии, не «exactly once».

- Отправка раз в 10 секунд, если очередь непустая; порог 20 событий; немедленно при достижении цели или наличии пустого сигнала проверки current.
- Одновременно один запрос, timeout 15 секунд. Новые события остаются в pending, отправленная пачка — в inFlight.
- Успех: заменить подтверждённый прогресс, удалить inFlight, сохранить новые pending. При ошибке/таймауте отправленная пачка выбрасывается без повторной отправки. Незаписанное при закрытии приложения теряется.
- Исключение: 401 обрабатывает общий callApi — refresh token и повтор отклонённого запроса. НЕ добавлять `_retry: true` в вызов достижений: это отключит обновление токена.
- При входе/выходе session сбрасывает прогресс/очередь/pins/награды; поздний ответ старого пользователя игнорируется.
- Между устройствами нет push-синхронизации; подтверждённое состояние получают с сервера. Удаление повторной награды защищено датой, но повтор обычного события count/sum не защищён.

Ответ:

```json
{
  "user_achievements": {"permanent": {}},
  "granted_rewards": [],
  "user_resources": null
}
```

Это ответ без выдачи награды. При выдаче `user_resources` содержит полный актуальный баланс, а элементы `granted_rewards` имеют форму:

```json
{
  "achievement_id": "example", "period_type": "permanent", "period": null,
  "rewards": {"resources": {"money": 100}}
}
```

Поля ответа обязательные. При непустом user_resources заменяем баланс целиком, не прибавляем reward поверх него.

## Бэк и награды

Сервис берёт каталог, блокирует прогресс `FOR UPDATE`, применяет события и выдаёт награды в одной транзакции. Для current читает свои данные: фронт отправляет только `{}`. Проверка прокачек блокирует user_upgrades до ресурсов, в том же порядке, что покупка прокачки. Для ресурсов используется настоящий баланс после серверных лимитов.

Награды сейчас только resources. Схема содержит `rewards.resources`; другие разновидности (cards/leaders) обсуждались как будущее расширение, не реализованы. granted_rewards содержит фактически выданную разницу до/после, в том числе нули при лимите. Сначала подтверждаем завершённые контракты, затем учитываем их ненулевые награды как `resource.gained`. Это может завершить следующий контракт. Награда за уже выполненный контракт не выдаётся снова.

## Проверки состояния при загрузке

Подписка `installAchievementSync` ждёт мутации:

- Баланс: set_resource, setUserAchievements, setAchievementsConfig.
- Прокачки: setUpgrades, setUserUpgrades, setUserAchievements, setAchievementsConfig.

После готовности каждой группы один раз вызывается соответствующая проверка. Она отправит пустой сигнал только если локально достигнута ещё не подтверждённая цель. Покупки при загрузке не создаются. После действий такие же проверки вызываются из централизованных обработчиков. Подписка на set_resource не означает автоматический учёт заработка при любом обновлении баланса.

`currentResources` показывает баланс, но подтверждение происходит на момент проверки БД. Если цель была кратковременно достигнута и деньги потрачены до проверки, контракт может не засчитаться. Снимки до/после операции могут захватить постороннее изменение баланса при параллельных запросах/наградах; это существующее ограничение, не обещать точный журнал операций.

## UI

Категории по ordering (при равенстве id), по умолчанию свёрнуты. Внутри сначала невыполненные по ordering/id, затем выполненные по completed_at от новых к старым. Фильтры «скрыть выполненные» / «только выполненные» взаимоисключающие, pinned отдельно.

До пяти pinned, только в памяти стора. Подтверждённые выполненные закрепить нельзя; при серверном подтверждении pin удаляется, локальный порог его не удаляет. В игровом инвентаре кнопка с существующим SVG меча слева от заголовка открывает pinned-модалку.

Награды — кастомные vue-toastification тосты справа, максимум три одновременно, очередь остальных; таймер 6 секунд запускается при отображении. Заголовок контракта фиксируется при ответе, ресурсы показываются фактические, нулевые скрыты. Учитывать узкую ширину приложения при любых CSS-изменениях. Не заменять SVG-ассет отдельным компонентом без необходимости.
