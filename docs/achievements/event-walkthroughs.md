Документ охватывает все типы событий, отправляемых на бэк. Локальные входы трекера упоминаются только там, где нужны для объяснения формирования события.

## Как продолжать работу с системой

Это единый справочник достижений Gridways: общие правила ниже, затем подробные главы всех событий. Примеры для копирования — [config-examples.json](config-examples.json). Они демонстрируют механизмы, а не заменяют каталог БД и не задают экономику игры. Код и текущие указания пользователя важнее документации. Общие правила сведены 2026-11-18.

При новой задаче сначала прочитать нужную главу события, затем сверить актуальный фронт и бэк. Новое значение фильтра обычно требует только конфига. Новый механизм требует согласовать типы, preview, серверную схему/обработчик и этот справочник. Не менять БД и не импортировать примеры без поручения.

### Карта кода и границы ответственности

- Типы/enum: `src/types/achievements.ts`. Трекер и чистые обработчики: `src/logic/achievements/`. Стор: `src/store/modules/achievements.ts`. Подключение синхронизации: `src/main.ts`.
- Компонент сообщает успешную операцию через trackAchievementEvent; снимки сохраняет до await. Конкретные задания проверяются централизованно. Обычные processResources, processCraftMillCard, openRelatedLevels, postUserUpgrade не содержат трекера.
- processAchievementEvents строит preview, syncAchievementEvents выбирает момент отправки, sendAchievementEvents в сторе делает HTTP-запрос и применяет ответ. Сервер подтверждает прогресс и награды.
- На фронте setAchievementsConfig один раз строит `achievementsByEvent` через `buildAchievementIndex`: Map с заданиями permanent по типу события. В индекс входят основной event и события counter.reset; Set исключает повтор одного задания в одном списке. Все вызовы processAchievementEvents и previewCurrentResources/Upgrades/Decks получают этот готовый индекс, а не каталог. При замене или очистке конфига индекс пересоздаётся; при выходе сохраняется вместе с permanent. Каталог обновляем через setAchievementsConfig, а не редактированием вложенных полей на месте. Подсчёт и replay очереди прежние; подготовка индекса больше не повторяется при каждом расчёте. На бэке `apply_events` также один раз на пачку строит индекс по основному событию и событиям сброса, без дублей и с сохранением порядка заданий. Обычные словари фильтров задания и его сбросов готовятся один раз на пачку, а награждённые задания пропускаются до проверки условий. Между запросами индекс и фильтры не кешируются: каталог заново читается и валидируется для каждого запроса. Порядок событий, приоритет сбросов, начисление наград и транзакция не изменены.
- Бэк — отдельный репозиторий GridwaysBackend: найти checkout или уточнить расположение. Не хранить персональные абсолютные пути в репозитории.
- На бэке: `services/api/app/apps/user_achievements/{schemas.py,routes.py,service.py}`, `logic/{events.py,filters.py,upgrades.py,decks.py,user_achievements.py}`. Загрузка прогресса — `apps/progress/service.py`, константы — `apps/game_data/logic/game_const.py`; модели — `lib/utils/models/game/achievements.py`, игровые enum — `lib/utils/schemas/game.py`.
- Понятность кода важна: явные if вместо вложенных тернарников; поля данных событий видны в своей модели, без наследования, скрывающего mode или другие поля. Не добавлять необязательные параметры без реального вызывающего кода.
- Импорт стора допустим только без чтения его состояния при загрузке модуля. Уже была ошибка Vuex getters из-за импорта константы через модуль стора: общие константы держать в чистом `logic/achievements/constants.ts`.

### Каталог и прогресс пользователя

```text
game_constants.data.achievements.permanent
  title
  categories
    <category_id>
      id, title, ordering
      achievements
        <achievement_id>
          id, title, ordering, event, filters, counter, target, rewards, group?
```

Категория вставляется в categories, задание — в её achievements. Повторная категория внутри achievements ломает карточку: у неё нет rewards.resources. Ключ задания совпадает с id; ID уникален между категориями секции. Для нового смысла уже выданного контракта нужен новый ID, иначе сохранятся прежние прогресс и награда.

В game_const могут храниться permanent/daily/weekly, но фронту приходит только permanent. get_game_constants на бэке исключает daily/weekly при чтении JSONB. Текущая обработка считает permanent; это важно при расширении периодических заданий. Для них существует achievement_sets с period_type, period_start, task_ids (список строк), уникальностью пары период/начало и историей общих наборов. Договорённость на будущее — общие выбранные сервером задания и прогресс периода `{period, tasks}`, а не индивидуальная случайная выдача.

`user_achievements.id = users.id`, progress — JSONB. Общая загрузка прогресса создаёт пустую запись, если её нет. POST событий предполагает, что запись уже создана.

```json
{
  "permanent": {
    "craft_all_inventory_items": {
      "value": 2,
      "seen": ["shields", "draw_cards"],
      "completed_at": null,
      "reward_granted_at": null
    }
  }
}
```

Категория в прогрессе не хранится: поиск по ID. Отсутствующее задание означает нулевой прогресс. Seen нужен для unique, streak — для текущей серии. Даты в UTC выставляет бэк. Локальный preview не меняет подтверждённые массивы seen по ссылке.

### Общие фильтры

Пути относительно event.data, например actor.color, spent.money. Все поля фильтра соединены И. Литерал означает строгое равенство без приведения числа к строке.

| Оператор | Значение |
|---|---|
| eq / ne | Строка, число, bool или null |
| gt / gte / lt / lte | Конечное число |
| in | Список скаляров: ИЛИ среди значений одного поля |
| exists | Bool: присутствует ли поле; null считается присутствующим |

Отсутствующее поле не проходит даже ne; отсутствие проверяется exists:false. Вложенные пути и индексы массивов поддерживаются; сегменты __proto__, prototype, constructor запрещены. Регистр игровых строк сохраняется: Bronze, Soldiers и т. п.

Для ИЛИ между разными условиями есть служебный ключ `any` — непустой список обычных наборов фильтров:

```json
"filters": {
  "enemy.color": { "type": "exists", "value": true },
  "any": [
    { "enemy.data.base.base_hp": { "type": "gte", "value": 50 } },
    { "hp_before_death": { "type": "gte", "value": 50 } }
  ]
}
```

Это карта врага И (базовое HP >= 50 ИЛИ HP перед смертельным действием >= 50). Соседние поля соединяются через И, внутри каждого варианта any тоже И; между вариантами — ИЛИ. Несколько совпавших вариантов не умножают прогресс: фильтр возвращает один boolean, затем счётчик применяется один раз.

Без any прежние конфиги работают как раньше. any разрешён и в filters каждого элемента counter.reset; приоритет сброса серии не меняется. Вложенный any, пустой список any и списки групп под другими ключами запрещены схемой бэка. Пустой filters или пустой набор `{}` внутри any не ограничивает событие — такой вариант делает группу any всегда подходящей. Отдельного all нет. Имя any зарезервировано на уровне набора фильтров; обычный путь вроде actor.any остаётся полем данных.

### Общие счётчики

| counter.type | Подсчёт |
|---|---|
| count | +1 за подходящее событие; field не нужен |
| sum | Прибавить положительное конечное число из field |
| unique | Добавить новое значение field (строку, число или JSON-объект) в seen; value — число разных значений |
| current | Заменить value числом из field; для ресурсов также максимумом из fields с aggregation: max; только checked-события |
| streak | Считать подходящие события подряд; length событий дают +1 к value |

Value ограничивается target. У unique число 1 и строка "1" различаются; null, bool и массив на верхнем уровне не считаются уникальным значением. Объект (например recipe) сохраняется в seen строкой `object:<JSON>` с отсортированными ключами, включая вложенные объекты. При сравнении запись разбирается обратно: 1 и 1.0 в JSON означают одно число. Порядок элементов вложенных массивов важен. Строки с префиксом object: или string: получают префикс string:, чтобы не смешиваться с объектами. Обычные строки и числовые ID хранятся как раньше. Хэша нет. Для «каждый предмет» нужен ограничивающий in-список и target, равный его длине. Проверять достижимость каждого элемента: наличие фракции в enum не доказывает наличие доступного лидера этой фракции.

У current допустимы только resources.checked, upgrades.checked, decks.checked; поля и источники описаны в их главах. До подтверждения значение может уменьшаться. Достижение target в preview ещё не означает подтверждение или награду.

У streak counter.reset — обязательный непустой массив `{event, filters}`. Любой совпавший элемент сбрасывает только текущий streak, не число завершённых серий value. Сброс проверяется раньше продвижения. Остальные события игнорируются. Серии непересекающиеся: после length событий streak обнуляется. Например, length 3 / target 5 — пять троек, length 10 / target 1 — одна десятка. Скрытый streak хранится на бэке между сессиями, в UI показывается только value/target. Завершённые контракты не сбрасываются. Порядок событий имеет значение; между устройствами это порядок обработки пачек, не глобальная история боя.

### Очередь, API и награды

В sendAchievementEvents есть одна проверка: если categories в сохранённом конфиге permanent пуст, запрос не отправляется. Отсутствующий ключ achievements при загрузке заменяется пустой секцией для стора. Отдельного флага включения нет; события продолжают накапливаться в памяти и могут отправиться после получения конфигов. Уже отправленный запрос завершается обычным образом. Изменение конфигов в БД влияет на открытый клиент только после повторного получения констант — автоматического опроса каталога нет.

POST `/user-achievements/{user_id}` принимает `{events: [{type, data}]}`. UUID используется только локально. Нет wire-ID, acknowledged_event_ids, серверной дедупликации, localStorage/outbox или гарантии доставки.

- Отправка каждые 10 секунд при непустой очереди, при 20 событиях, сразу при достигнутой цели или checked-сигнале.
- Один запрос одновременно; timeout 15 секунд. Отправленные события — inFlightEvents, новые — pendingEvents.
- При успехе подтверждённый прогресс заменяется ответом, inFlight удаляется. При сетевой ошибке/таймауте пачка выбрасывается без повтора. Закрытие приложения теряет неотправленное.
- 401 обрабатывается штатным refresh/retry в callApi. Не ставить `_retry: true`: это отключает обновление токена для запроса.
- Session защищает от позднего ответа другого аккаунта; вход/выход сбрасывает очередь, прогресс, pins и уведомления. Push-синхронизации устройств нет.

```json
{
  "user_achievements": {"permanent": {}},
  "granted_rewards": [],
  "user_resources": null
}
```

Все ключи ответа обязательны. Null-баланс не меняет ресурсы; непустой user_resources заменяет баланс целиком. Элемент granted_rewards содержит achievement_id, period_type, period и rewards.resources с фактически выданными суммами. Сервис блокирует прогресс и сохраняет его с наградой в одной транзакции. Дата награды предотвращает повторное награждение, но не удвоение незавершённого count/sum при повторной отправке события.

Награды сейчас — только ресурсы; конфиг `rewards: {resources: {money: 100}}`, количества целые неотрицательные. Лимиты применяет игровой бэк, ответ содержит фактическую разницу, включая возможные нули. Сначала подтверждаем контракт, затем учитываем ненулевую награду как доход и проверяем current. Так возможна цепочка разных наград без повторного награждения первого контракта.

LocalUserAchievements для UI — подтверждённый прогресс + replay inFlight/pending + актуальные снимки current. Не начислять награду и не ставить completed_at по локальному preview.

### Отображение, группы и закрепления

Категории сортируются по ordering и по умолчанию закрыты. Внутри сначала невыполненные, выполненные — по времени завершения от нового. Фильтры «скрыть выполненные» / «только выполненные» взаимоисключающие; есть фильтр закреплённых.

Необязательный group сворачивает невыполненные задания одной категории в строку со стрелками. В группе сортировка target, ordering, id, по умолчанию ближайшая оставшаяся цель. Строка сортируется по минимальному ordering. Завершённые задания отдельные; фильтры применяются до группировки. Выбор хранится по ID в компоненте; закрепляется показанный контракт, не вся группа. Счётчик категории считает задания, не строки. Group не влияет на подсчёт или хранение прогресса. Код — displayGroups.ts и AchievementGroupRow.vue.

До пяти закреплений, только в сторе. AchievementCard проверяет лимит/выполнение и вызывает простую мутацию toggleAchievementPin; отдельного action для переключения нет. PrunePins убирает подтверждённые выполненные и исчезнувшие задания. Локальный target не удаляет pin. Общая константа лимита — в чистом constants.ts.

Награды показываются кастомными vue-toastification тостами справа: максимум три, остальные в очереди, 6 секунд с момента показа. Заголовок фиксируется из конфига при ответе, нулевые ресурсы скрываются. Сохранять ограничения нестандартной ширины приложения; использовать существующие SVG.

### Проверка изменений и примеров

В [config-examples.json](config-examples.json) оставлены характерные сочетания пяти счётчиков, восьми операторов, серий, групп и разных событий. Не размножать примеры только ради нового порога/цвета и не импортировать весь файл поверх каталога. Копировать нужное задание/категорию, проверяя вложенность, имена и экономику.

Конфиги сверять с примерами и актуальными моделями в backend user_achievements/schemas.py, а также с типами и обработчиками фронта. Отдельно проверять уникальность ID, вложенность, доступность игровых объектов, достижимость целей и экономику. Не запускать backend tests без нового прямого разрешения пользователя. Не создавать frontend tests/ по умолчанию; использовать относящиеся type/lint проверки и при необходимости временные проверки поведения.

Не считать любое изменение ресурсов подключённым автоматически: вызовы трекера явные. При расширении искать processResources, set_resource и альтернативные ответы с балансом. Расходы аренных прокачек и оплаченные покупки были оставлены отдельно; проверять актуальные места вызова, прежде чем обещать их учёт. Обычный GET не является заработком. ProcessCraftBonusCard пополняет коллекцию из бонуса, не означает платный craft.

При рефакторинге сохранять действия пользователя, текущие конфиги и уже выданные награды. Обновлять этот справочник по конечному поведению, не оставлять историю устаревших миграций и ссылок на удалённые SQL.


## GameWon — победа в бою

### Как событие доходит до проверки контракта

**1. WinPage или ArenaWinPage вызывает:**

```ts
trackAchievementEvent({
  type: AchievementEventType.GameWon,
})
```

Вызов находится в `created`, после проверки одноразового `win_redirect` и до дальнейшей обработки победы. Флаг сразу снимается: повторное открытие страницы не создаёт новую победу. Обычные сезоны, random/random_n и мультиплеер используют WinPage, арена — ArenaWinPage.

**2. Мастер-функция вызывает finishAchievementBattle.**

Она собирает данные из стора:

```ts
{
  mode,
  difficulty,
  starting_deck: { cards, leader },
  battleStats,
  enemy_grave,
}
```

Мастер-функция делает независимую JSON-копию этих данных и кладёт событие в `pendingEvents` через мутацию `enqueueAchievementEvent`. Дальнейшие изменения объектов игры уже не меняют событие в очереди.

**3. Событие из очереди получает processAchievementEvents.**

Именно в этой функции находится ветка, добавляющая `starting_deck.summary`. Её вызывают в двух случаях:

- Для отображения прогресса: геттер `localUserAchievements` передаёт ей подтверждённый прогресс и события из очередей `inFlightEvents`, затем `pendingEvents`.
- Для немедленной отправки: подписка на добавление события проверяет, достигли ли мы цели контракта. Для этого `shouldFlush` тоже вызывает `processAchievementEvents` — сначала для уже отправленной пачки, затем для новых событий.

Это два независимых расчёта от переданных исходных данных, а не два прибавления к сохранённому прогрессу. Если очередь уже достигла лимита, планировщик может отправить её без расчёта достижения цели.

**4. Внутри перебора событий встречается наша победа:**

```ts
for (const event of events) {
  let data = event.data

  if (event.type === AchievementEventType.GameWon) {
    // Вот мы и здесь.
  }
}
```

Здесь к данным колоды добавляется вычисленная `summary`, а дальше в этой же функции проверяются фильтры контрактов — например:

```json
"starting_deck.summary.all_bronze": true
```

То есть `summary` нужна для расчёта условий. Она добавляется к локальным данным обработки; **событие в очереди остаётся без неё**. Когда оно уйдёт на бэк, бэк самостоятельно посчитает такую же сводку.

### Откуда берётся каждое поле

| Поле в data | Источник и смысл |
|---|---|
| `mode` | `finishAchievementBattle()` вызывает `resolveAchievementGameMode()`, которая сама читает игровой стор: multiplayer по имени уровня, затем arena_mode, затем random_n/random, иначе normal. В вызов GameWon режим не передаётся. |
| `difficulty` | `store.state.game.level?.difficulty`. Если уровня нет, значение undefined не попадёт в JSON. |
| `starting_deck.cards` | `store.state.game.current_deck.map(entry => entry.card)`: полные объекты карт, без обёрток пользовательских записей. Не остаток игровой колоды и не рука. |
| `starting_deck.leader` | Текущий `store.state.game.leader`. Если лидер в сторе заменился, берём уже его. |
| `battleStats.leader_uses` | Число из `store.state.achievements.battleStats.leader_uses`: сколько раз применён заряд лидера за бой. Не вычисляется по оставшимся зарядам. |
| `enemy_grave.total` | `store.state.game.enemies_grave.length`. Лидер в кладбище не попадает; единицу за него не прибавляем. |
| `enemy_grave.bronze/silver/gold` | Число элементов этого же кладбища с color Bronze/Silver/Gold. Это состав кладбища на победе, не история убийств. |

`starting_deck` — имя поля события, а не отдельное поле игрового стора. Оно объединяет карты и лидера для фильтров контрактов. Отдельной копии исходной колоды в модуле достижений нет: игра работает с копиями, а при победе читаем игровой стор.

Откуда берётся `battleStats.leader_uses`: при начале боя `startAchievementBattle()` обнуляет счётчик. Затем каждое применение заряда лидера прибавляет 1. Срабатывание пассивной способности лидера зарядом, сыгранным игроком, не считается. Поэтому при победе `battleStats.leader_uses = 0` означает, что игрок ни разу не применил заряд лидера.

### Что отправляется на бэк

Экшен `sendAchievementEvents` отправляет POST `/user-achievements/{user_id}` с `events`. Ни локального UUID, ни вычисленной `summary` в передаваемом событии нет.

Пример формы запроса ниже. Для компактности в cards и leader показаны только некоторые поля: в реальном событии отправляются полные объекты из стора. Значения демонстрационные.

```json
{
  "events": [
    {
      "type": "game.won",
      "data": {
        "mode": "normal",
        "difficulty": "hard",
        "starting_deck": {
          "cards": [
            { "id": 1, "color": "Bronze", "faction": "Soldiers" },
            { "id": 2, "color": "Bronze", "faction": "Neutral" }
          ],
          "leader": { "id": 13, "faction": "Soldiers" }
        },
        "battleStats": { "leader_uses": 0, "damage_taken": 0, "enemy_passives_in_field": 0 },
        "enemy_grave": { "total": 35, "bronze": 10, "silver": 5, "gold": 20 }
      }
    }
  ]
}
```

### Статистика текущего боя

В сторе battleStats содержит leader_uses, damage_taken и enemy_passives_in_field. Одна мутация incrementAchievementBattleStat принимает key и amount; startAchievementBattle сбрасывает все показатели. В начале боя сброс выполняется до эффектов начала игры.

Damage_taken суммирует величину прошедшего урона в damage_player и при применении attack_log у второго игрока. Поглощение бронёй/неуязвимостью не считается; лечение не уменьшает сумму. Передаётся сам damage без сравнения здоровья до/после и без ограничения оставшимися HP: удар на 100 при 3 HP добавляет 100. Прямой начальный DamageOnce и установка HP сейчас не вызывают этот счётчик.

Enemy_passives_in_field увеличивается после допуска таймером и вызова поддерживаемого обработчика field_passives, даже при бесполезном эффекте. Пустая/неизвестная пассивка не считается. Сюда входит пассивка лидера врагов, которую игровой диспетчер относит к полю; колода и сброс не входят.

В мультиплеере каждый учитывает собственный прошедший урон после своей защиты, без повторного запуска damage_player при получении attack_log. Leader_uses также остаётся личным. Счётчик пассивок поля между игроками не синхронизируется: локально учитываются только запущенные на этом клиенте обработчики. Контракт «сложная победа без пассивок врагов на поле» используется только с mode = normal и difficulty = hard; для мультиплеера этот показатель не описывает весь бой.

Фильтры победы: battleStats.damage_taken = 0, battleStats.enemy_passives_in_field = 0, battleStats.leader_uses = 0. Счётчик контракта — обычный count. На бэке GameWonData требует AchievementBattleStats с тремя явно указанными неотрицательными полями. Старый фильтр leader_uses нужно вручную заменить на battleStats.leader_uses в каталоге БД; SQL автоматически не выполняется.

### Что вычисляется при обработке

Фронт вызывает `buildDeckSummary`, бэк — `build_deck_summary`. Обе функции получают cards и считают одинаковые признаки; лидер в сводку не входит.

| Поле starting_deck.summary | Значение |
|---|---|
| `cards_count` | Число карт |
| `by_color.Bronze/Silver/Gold` | Число карт каждого цвета |
| `neutral_count` | Число карт фракции Neutral |
| `all_bronze/all_silver/all_gold` | Колода непустая и все карты указанного цвета |
| `all_neutral` | Колода непустая и все карты Neutral |
| `no_neutral` | Колода непустая, у каждой карты известна фракция и ни одна не Neutral |

Пустая колода не получает флаги «все бронзовые» или «без нейтральных». Сводка пересчитывается из карт, даже если клиент прислал собственную summary.

### Что сейчас делает бэк

1. Схема `GameWonEvent` проверяет входное событие. В `GameWonData` обязательны mode, difficulty, starting_deck, battleStats и enemy_grave. В составе колоды обязательны cards (список объектов карт) и leader (объект лидера). Внутри карт и лидера сохраняются все игровые поля. Неполное событие или неправильный тип отклоняются до подсчёта.
2. `apply_events` превращает data из Pydantic-модели в словарь.
3. Добавляет в `data["starting_deck"]["summary"]` сводку, рассчитанную из `event.data.starting_deck.cards`. Структура уже проверена схемой, поэтому повторная проверка dict не нужна. Входная модель не изменяется. Очистки None нет: обязательные поля победы не допускают null, а вложенные null в игровых объектах сохраняются для фильтров.
4. Общий обработчик проверяет event и filters каждого задания, обновляет соответствующий счётчик и собирает награды. Сервис сохраняет прогресс и начисляет награды в транзакции. Ответ затем заменяет подтверждённый прогресс на фронте.

Бэк здесь не воспроизводит бой: исходные карты, применения лидера и состав кладбища сообщает клиент. Пересчёт summary проверяет состав переданных карт, а не достоверность победы.

### Какие контракты можно описать

Ниже указаны условия, а не полные конфиги. Для всех строк event = `game.won`; обычный режим ограничивается `"mode": "normal"`. Несколько фильтров соединяются через И.

| Контракт | Дополнительные filters | counter и target |
|---|---|---|
| Победите 100 раз | Нет | count, 100 |
| Победите 100 раз за Soldiers | `starting_deck.leader.faction = Soldiers` | count, 100 |
| Победите 3 раза бронзовой колодой | `starting_deck.summary.all_bronze = true` | count, 3 |
| Победите без золотых карт | `starting_deck.summary.cards_count > 0`, `starting_deck.summary.by_color.Gold = 0` | count, 1 |
| Победите на сложном уровне 100 раз | `difficulty = hard` | count, 100 |
| Победите без применения лидера 3 раза | `battleStats.leader_uses = 0` | count, 3 |
| Победите с минимум 30 врагами в кладбище 5 раз | `enemy_grave.total >= 30` | count, 5 |
| Победите с минимум 20 золотыми в кладбище 5 раз | `enemy_grave.gold >= 20` | count, 5 |
| Выиграйте 3 боя подряд — 5 серий | Нет | streak, length 3, target 5; reset по game.lost того же режима |

Порог 30/50/70, цвет или режим меняются конфигом. Возможны и другие общие счётчики: например unique по starting_deck.leader.id или sum по enemy_grave.gold. `current` для game.won не применяется — он предназначен для отдельных проверок состояния.

Фильтры работают и по другим доступным полям полных объектов. Это не отдельные проверки в коде для каждого задания. Операторы и счётчики описаны в разделах [общих фильтров](#общие-фильтры) и [общих счётчиков](#общие-счётчики), готовые характерные примеры — в [config-examples.json](config-examples.json).

## GameLost — поражение в бою

### Как событие доходит до сброса серии

**1. Игровой код обнаруживает поражение и вызывает:**

```ts
trackAchievementEvent({
  type: AchievementEventType.GameLost,
})
```

Есть три места вызова:

- `check_lose`: здоровье игрока стало <= 0, перед переходом на страницу поражения.
- `MultiplayerGamePage`: наблюдатель здоровья обнаружил поражение вне своего хода, при инициализированной и ещё не завершённой игре.
- `MultiplayerGamePage`: получено сообщение GAME_END с поражением, перед переходом на страницу поражения.

Сама LosePage событие не создаёт. Простой выход из игры и отключение от матча без зафиксированного поражения тоже не создают GameLost.

**2. Мастер-функция собирает событие и кладёт его в очередь.**

Режим не передаётся аргументом. `resolveAchievementGameMode()` сама читает игровой стор: multiplayer по имени уровня, затем arena_mode, затем random_n/random, иначе normal. После multi_reset имя уровня остаётся в игровом сторе, поэтому режим по-прежнему определяется как multiplayer.

У события есть локальный UUID и всего одно поле data — mode. Здесь не нужны ни колода, ни лидер, ни кладбище. Ветка сразу вызывает `enqueueAchievementEvent` и возвращает локальный ID; до общей подготовки остальных событий выполнение не доходит.

**3. processAchievementEvents получает поражение из очереди.**

Как и для победы, предварительный расчёт вызывается для отображения прогресса и проверки необходимости отправки пачки. Для серий задание ищется не только по основному event, но и по событиям из counter.reset. Поэтому game.lost находит контракт, у которого основное событие — game.won.

**4. Совпало условие reset — обнуляем только streak.**

Например, контракт требует выиграть 3 боя подряд, повторить это 5 раз:

```json
{
  "event": "game.won",
  "filters": { "mode": "normal" },
  "counter": {
    "type": "streak",
    "length": 3,
    "reset": [
      { "event": "game.lost", "filters": { "mode": "normal" } }
    ]
  },
  "target": 5
}
```

Это фрагмент условий контракта, без названия, ID и награды. Если было `value = 2, streak = 2`, после поражения будет `value = 2, streak = 0`: две полные серии остаются, две победы текущей незаконченной серии теряются. Подтверждённые выполненные контракты не меняются. Поражение другого режима этот reset не проходит.

Проверки «бой ещё активен» в трекере нет. Повторное поражение тоже попадёт в очередь: для такого reset два последовательных сброса дают тот же нулевой streak. Это свойство сброса, а не общая защита от повторов событий.

### Что отправляется на бэк

```json
{
  "events": [
    {
      "type": "game.lost",
      "data": { "mode": "normal" }
    }
  ]
}
```

Локальный ID не отправляется. Поражение использует обычную очередь: каждые 10 секунд при наличии событий, при достижении размера пачки или другой причины немедленной отправки. Сам по себе сброс серии не означает выполнение контракта и не требует немедленного запроса.

Порядок событий сохраняется: если после поражения начался следующий бой и пришла победа, обработчик сначала сбросит серию, затем прибавит новую победу. Принятое правило потери неотправленных событий распространяется и на поражения: если событие потерялось, сервер не узнает о сбросе.

### Что делает бэк и какие контракты доступны

`GameLostData` явно содержит одно обязательное поле mode. Схема проверяет его, затем `apply_events` превращает data в словарь и передаёт в общую обработку. Специального расчёта или добавления summary для поражения нет.

Обработчик streak сначала проверяет все условия reset. Если одно совпало, обнуляет streak незавершённого задания, сохраняя value и ранее выданные награды. Текущий смысл GameLost в контрактах — сбрасывать серии побед выбранного режима.

Технически общий механизм также позволяет сделать самостоятельный контракт с `event: game.lost` и `counter: count`, но тогда каждое повторно отправленное событие считается отдельным поражением. Для принятого использования как reset такой подсчёт не нужен. Проверки колоды, сложности или количества врагов по этому событию невозможны: в нём есть только mode.

## ActionPlayed — применение заряда карты или лидера

### Как событие доходит до проверки контракта

**1. Игрок применяет карту или лидера.**

В [player_move.ts](../../src/logic/player_move/player_move.ts) есть два места вызова:

- `damage_ai_card` — применение к одной цели.
- `damage_ai_card_multi` — применение к нескольким целям. Вызов трекера стоит после цикла целей, поэтому несколько поражённых врагов не превращаются в несколько сыгранных зарядов.

Это два варианта обработки хода, а не два обязательных вызова на каждый ход. Оба получают `card: Card | Leader`.

**2. До эффекта хода сохраняем объект для достижения.**

```ts
const achievementActor = copyObj(card)
```

В нём остаются значения до эффекта и расхода заряда: например, текущий урон, число зарядов, способность и пассивка. Это полный объект конкретной сыгранной карты/лидера, а не повторная загрузка базовой карты по ID.

Сообщаем о применении:

```ts
trackAchievementEvent({
  type: AchievementEventType.ActionPlayed,
  actor: achievementActor,
})
```

Один такой вызов означает один применённый заряд. Не требуется, чтобы способность обязательно нанесла урон или убила врага. Реакции пассивок на ход обрабатываются далее отдельно и не создают дополнительные ActionPlayed.

**3. Мастер-функция отдельно учитывает применение лидера.**

Если у actor нет поля color, это лидер. Тогда `incrementAchievementBattleStat` прибавляет 1 к локальному `battleStats.leader_uses`. Это нужно для будущего события GameWon и контракта «победите без применения лидера».

При этом само ActionPlayed не пропускается: оно подходит для контрактов на заряды лидера. У карты есть color, поэтому её применение не увеличивает leader_uses. Здесь проверяется наличие поля, а не значение цвета.

**4. Формируем данные события и кладём в очередь.**

```ts
eventData = {
  actor: input.actor,
  mode: resolveAchievementGameMode(),
}
```

Мастер-функция создаёт независимую JSON-копию, добавляет локальный UUID и вызывает `enqueueAchievementEvent`. Первая копия в player_move сохранила состояние до эффекта; эта копия отделяет данные очереди от переданного объекта.

**5. processAchievementEvents проверяет контракты.**

Как и для GameWon, расчёт вызывается для предварительного прогресса интерфейса и для решения, пора ли немедленно отправить пачку. Для ActionPlayed дополнительной сводки нет: фильтры читают actor и mode непосредственно из события.

Например, один бронзовый заряд может одновременно продвинуть задания на 10 бронзовых зарядов, 20 бронзовых зарядов и игру карт фракции Soldiers. Обработчик не содержит отдельных веток для этих заданий — условия находятся в конфиге.

### Что отправляется и откуда берутся поля

| Поле | Источник |
|---|---|
| `actor` | Полная копия аргумента card из player_move, снятая до эффекта хода и расхода заряда |
| `mode` | Текущий игровой стор, который читает resolveAchievementGameMode() |

Внешний запрос содержит массив events. Ниже один пример; поля actor сокращены для чтения, реальные вложенные объекты отправляются полностью.

```json
{
  "events": [
    {
      "type": "action.played",
      "data": {
        "actor": {
          "id": 7,
          "color": "Gold",
          "faction": "Soldiers",
          "type": "Unit",
          "ability": { "name": "damage-one" },
          "passive_ability": { "name": "incr-self-dmg" },
          "data": {
            "damage": 7,
            "charges": 2,
            "base": { "base_damage": 7, "base_charges": 2 }
          }
        },
        "mode": "normal"
      }
    }
  ]
}
```

Для лидера форма события такая же, но actor — полный объект лидера без color. Отдельного события leader.played нет. Локальный UUID на бэк не отправляется. leader_uses также не входит в ActionPlayed: его итог передаётся при победе.

Карты, созданные из врагов через `enemy_as_card`, получают `from_enemy: true`. Через эту функцию проходят захват врага в руку и создание карт из врагов в руку/колоду, включая специальные способности. Флаг сохраняется при копировании целого объекта и переносе между игровыми зонами. Он попадает в actor через существующий снимок в player_move; отдельного события или вызова трекера нет. Само получение карты не двигает контракт «сыграйте»: учитывается применение каждого её заряда.

У обычных карт поле отсутствует. Для контракта на карты врага нужен `"actor.from_enemy": true`; для исключения таких карт — `"actor.from_enemy": {"type": "exists", "value": false}`. Проверка ne true не подходит: отсутствующие поля не проходят ne. Без фильтра происхождения существующие задания по цвету/фракции продолжают учитывать и карты врагов.

ID превращённой карты остаётся ID врага. Поэтому unique по actor.id для смешанного набора своих и вражеских карт может объединить одинаковые числовые ID; для подсчёта разных видов вражеских карт ограничиваем контракт from_enemy:true. Механика unique не менялась.

### Что делает бэк

`ActionPlayedData` явно содержит `actor: dict[str, JsonValue]` и обязательный mode. Проверяется форма события; внутри actor разрешены произвольные JSON-поля, чтобы новые фильтры по уже переданным полям не требовали изменения схемы.

`apply_events` переводит data в словарь и сразу использует общие условия и счётчики. Специального преобразования ActionPlayed, вычисления summary или увеличения отдельного счётчика применений лидера на бэке нет. Бэк не выполняет способность повторно и не списывает заряд — событие только сообщает о совершённом действии.

Пути фильтров начинаются от data: `actor.color`, `actor.ability.name`, `actor.data.damage`. Значения цветов сохраняют регистр: Bronze/Silver/Gold. faction — строка, поэтому используется `actor.faction`, не `actor.faction.name`.

### Какие контракты можно описать

Все строки ниже используют event = `action.played`. Если нужен обычный режим, добавляем `"mode": "normal"`; без этого фильтра учитываются все режимы.

| Контракт | filters | counter |
|---|---|---|
| Примените бронзовые карты 10 раз | `actor.color = Bronze` | count, target 10 |
| Примените карты, созданные из врагов, 3 раза | `actor.from_enemy = true` | count, target 3 |
| Примените заряды лидера 10 раз | `actor.color exists false` | count, target 10 |
| Примените 30 разных карт | `actor.color exists true` | unique по actor.id, target 30 |
| Примените лидеров трёх фракций | `actor.color exists false`, faction in нужные фракции | unique по actor.faction, target 3 |
| Примените бронзовые карты Soldiers | `actor.color = Bronze`, `actor.faction = Soldiers` | count |
| Примените бронзовую карту с уроном >= 8 | `actor.color = Bronze`, `actor.data.damage >= 8` | count |
| Примените карту со способностью damage-all | `actor.color exists true`, `actor.ability.name = damage-all` | count |
| Примените Special-карту без пассивки | `actor.color exists true`, `actor.type = Special`, `actor.passive_ability.name = null` | count |

Обычные условия в filters соединяются через И. Если нужны Monsters ИЛИ Animals, достаточно одного фильтра `actor.faction` с оператором in. Для разных наборов условий используется any. Отсутствующее поле отличается от null: условие `actor.passive_ability.name = null` требует существующего поля со значением null.

Событие передаёт параметры сыгранного объекта, а не результат способности. Например, actor.data.damage — урон карты перед ходом, не фактически нанесённый всем целям урон.

### Серия: примените бронзовые карты 10 раз подряд

Полный пример задания для вставки в achievements категории cards:

```json
{
  "play_bronze_streak_10": {
    "id": "play_bronze_streak_10",
    "title": "Примените бронзовые карты 10 раз подряд",
    "ordering": 60,
    "event": "action.played",
    "target": 1,
    "counter": {
      "type": "streak",
      "length": 10,
      "reset": [
        {
          "event": "action.played",
          "filters": {
            "mode": "normal",
            "actor.color": { "type": "ne", "value": "Bronze" }
          }
        },
        {
          "event": "action.played",
          "filters": {
            "mode": "normal",
            "actor.color": { "type": "exists", "value": false }
          }
        }
      ]
    },
    "filters": { "mode": "normal", "actor.color": "Bronze" },
    "rewards": { "resources": { "money": 1000 } }
  }
}
```

- Каждый заряд любой бронзовой карты в normal продолжает серию. Карты могут быть разными; одинаковый actor.id здесь не требуется.
- Другой цвет сбрасывает серию первым условием reset, применение лидера — вторым. Одного ne Bronze недостаточно: отсутствующий у лидера color не проходит ne.
- Пассивки, события врагов, победы, поражения и действия в других режимах эту серию не сбрасывают. Поэтому она продолжается между боями, а не ограничивается одним уровнем.
- На десятом подходящем заряде value увеличивается на 1, streak обнуляется. target 1 означает одну полную серию, target 5 — пять непересекающихся серий.
- Сам streak скрыт в интерфейсе; отображается число завершённых серий value/target. При достижении цели очередь получает основание для немедленной отправки, награда подтверждается бэком.

Механизм уже общий для фронта и бэка: для такого задания достаточно конфига. Награда в примере демонстрационная.

## PassiveTriggered — активация пассивной способности

### Как событие доходит до проверки контракта

**1. Игровой обработчик запускает пассивку и сохраняет её владельца.**

Перед эффектом создаётся `actor = copyObj(card)` или `copyObj(leader)`. Это полный объект того, чья пассивка сработала. Если игра одной карты вызвала реакцию лидера, actor — лидер, а не сыгранная карта.

**2. После обработки сообщаем об активации:**

```ts
trackAchievementEvent({
  type: AchievementEventType.PassiveTriggered,
  actor,
  location: "passive_upon_playing_a_card",
})
```

`location` — имя поля. Строка справа — одно из разрешённых значений. Добавление строки в AchievementPassiveLocation расширяет допустимые значения этого поля, а не добавляет новое поле в объект события.

Есть четыре источника события, у них немного разный смысл «сработала»:

| Источник | Когда создаётся событие | location |
|---|---|---|
| `run_passive` | Таймер разрешил запуск и вызван поддерживаемый обработчик. Даже если эффект оказался бесполезен, это активация. При отказе таймера или неизвестной способности события нет. | hand/deck/grave, как передал вызывающий код |
| `passives_upon_beginning` | Обработчик разовой пассивки в начале боя вернул true. | passive_once |
| `passives_upon_playing_a_card` | Реакция конкретной карты на игру карты вернула true. Событие для каждой сработавшей карты. | passive_upon_playing_a_card |
| `leader_passive_abilities_upon_playing_a_card` | Реакция лидера на игру карты вернула true. Максимум одно событие за вызов диспетчера, даже при нескольких целях. | leader_passive_upon_playing_a_card |

Список карт для реакции на ход по-прежнему выбирается по флагам пассивки в руке/колоде/сбросе. Новое location только отделяет этот вид активации в контрактах, не меняет игровые условия работы способности.

**3. Мастер-функция добавляет режим и ставит событие в очередь.**

```ts
eventData = {
  actor: input.actor,
  mode: resolveAchievementGameMode(),
  location: input.location,
}
```

Далее — независимая JSON-копия, локальный UUID и `enqueueAchievementEvent`. Счётчик leader_uses не увеличивается: он относится к сыгранным зарядам ActionPlayed, а не к пассивкам.

**4. Фронт и бэк применяют общие фильтры и счётчики.**

Предварительный расчёт использует actor, mode и location без дополнительной сводки. На бэке `PassiveTriggeredData` явно описывает эти три обязательных поля: actor — полный JSON-объект, mode — режим, location — одно из шести разрешённых значений. В `apply_events` отдельной ветки для пассивок нет: работают обычные filters и counter. Бэк не запускает способность повторно и не вычисляет, был ли её эффект полезен.

### Что означает location

| Значение | Смысл |
|---|---|
| `hand` | Обычная пассивка в руке; обычная пассивка лидера тоже использует hand |
| `deck` | Обычная пассивка в колоде |
| `grave` | Обычная пассивка в сбросе |
| `passive_once` | Разовая пассивка в начале боя |
| `passive_upon_playing_a_card` | Реакция карты на сыгранную карту, независимо от зоны владельца |
| `leader_passive_upon_playing_a_card` | Реакция лидера на сыгранную карту |

Название поля сохранено, но для последних трёх значений оно обозначает ситуацию запуска, а не физическую зону. Лидер отличается от карты отсутствием actor.color.

### Что отправляется на бэк

Пример реакции лидера; actor сокращён для чтения, в запросе он полный:

```json
{
  "events": [
    {
      "type": "passive.triggered",
      "data": {
        "actor": {
          "id": 13,
          "faction": "Soldiers",
          "passive_ability": { "name": "add-charges-to-leader-if-play-special" }
        },
        "mode": "normal",
        "location": "leader_passive_upon_playing_a_card"
      }
    }
  ]
}
```

Значения actor демонстрационные; имя способности берётся из реального объекта, не назначается трекером. Локальный UUID не отправляется.

### Какие контракты можно описать

Для всех строк event = `passive.triggered`, counter = count, target — нужное число активаций. Для ограничения режима добавляем mode. Несколько фильтров соединяются через И.

| Контракт | filters |
|---|---|
| Пассивки карт в руке | location = hand, actor.color exists true |
| Пассивки карт в колоде или сбросе | location = deck или grave соответственно, actor.color exists true |
| Все пассивки лидера | actor.color exists false, без ограничения location |
| Только обычная пассивка лидера | actor.color exists false, location = hand |
| Разовые пассивки начала боя | location = passive_once |
| Реакции карт на ход | location = passive_upon_playing_a_card |
| Реакции лидера на ход | location = leader_passive_upon_playing_a_card |
| Любая реакция на ход | location in [passive_upon_playing_a_card, leader_passive_upon_playing_a_card] |
| Пассивки бронзовых карт с уроном >= 8 | actor.color = Bronze, actor.data.damage >= 8 |

Можно дополнительно фильтровать фракцию, имя пассивки и любые переданные поля actor. Урон и прочие параметры относятся к снимку до эффекта, а не к фактическому результату пассивки. Общий unique также подходит, например по actor.id для разных карт, с actor.color exists true для исключения лидеров.

## ArmorGained и InvulnerabilityGained — получение защиты игроком

События `armor.gained` и `invulnerability.gained` означают фактический прирост защиты, а не применение карты с соответствующей способностью.

### Источник и запрос

`add_armor` в `ability_armor.ts` запоминает броню до `change_armor`, затем передаёт разницу после мутации в трекер. `add_invulnerability` в `ability_invulnerability.ts` аналогично использует значение до/после `set_invulnerability`. Мутации уже ограничивают итог максимумом прокачки; правила начисления не меняются.

Если было 8 брони, максимум 10, а способность дала 5 — amount равен 2. Если максимум уже достигнут, функция возвращается без события. Нулевой, отрицательный или неконечный прирост также отбрасывается мастер-функцией.

```json
[
  { "type": "armor.gained", "data": { "amount": 2, "mode": "normal" } },
  { "type": "invulnerability.gained", "data": { "amount": 3, "mode": "normal" } }
]
```

Mode добавляет трекер через resolveAchievementGameMode. Amount — единицы брони либо добавленные ходы неуязвимости. Actor/предмет/причина в этих событиях не передаются. Общие функции покрывают начисления способностями карт и лидеров, пассивками и предметами инвентаря.

Начальная установка защиты, её расход, уменьшение длительности и сброс при старте игры не являются получением. В мутациях стора трекера нет. В мультиплеере учитывается личное получение защиты через эти функции; применение состояния напарника не создаёт повторного события.

### Подсчёт

| Контракт | event | counter |
|---|---|---|
| Получите броню N раз | armor.gained | count |
| Получите суммарно N брони | armor.gained | sum, field: amount |
| Получите неуязвимость N раз | invulnerability.gained | count |
| Получите суммарно N ходов неуязвимости | invulnerability.gained | sum, field: amount |

Одно получение 5 единиц даёт +1 для count и +5 для sum. Примеры в категории cards не ограничивают режим. Для конкретного режима добавляется filters.mode. Можно также фильтровать amount, например получение не менее 3 единиц за один раз.

На бэке явные модели `ArmorGainedData` и `InvulnerabilityGainedData` содержат положительный конечный amount и mode. Обработка общая, через filters/count/sum; события повторно защиту не начисляют. Бэк достижений принимает фактический прирост от клиента, игровое состояние боя не пересчитывает.

## EnemyEffectPlaced — враг разместил эффект на поле

Событие `enemy.effect_placed` создаётся сразу после записи эффекта в клетку: в `effects_passives.ts` (обычное/случайное размещение) и `effects_deathwish.ts` (обычное/случайное/массовое размещение). Пустая попытка без настроек эффекта или свободной клетки события не создаёт. Случайное размещение также требует непустого списка негативных эффектов. Индекс клетки 0 допустим.

Вызов мастер-функции передаёт enemy и effect. Трекер добавляет mode из игрового стора и копирует данные в очередь:

```json
{
  "type": "enemy.effect_placed",
  "data": {
    "enemy": { "id": 7, "color": "Bronze", "faction": "Soldiers" },
    "effect": { "type": "heal", "value": 3, "turns": 2, "negative": true },
    "mode": "normal"
  }
}
```

Enemy в примере сокращён; реально передаётся полный объект источника. Effect содержит параметры фактически записанного эффекта. У случайного размещения это уже выбранный тип, а не шаблон `field_interaction`. Снимок создаётся после записи, до звука; последующее уменьшение длительности эффекта не меняет событие.

Один эффект в одной клетке — один факт для count. Массовое завещание, заполнившее 4 клетки, даёт 4 события. Завещание, заменившее старый эффект в клетке умершего врага, также считается размещением. Усиление/продление, удаление и срабатывание уже существующего эффекта сюда не относятся. Эффекты игрока и начальная раскладка уровня не учитываются.

Событие универсально для эффектов врага: негативные выбираются фильтром `effect.negative: true`, как в примере `make_enemy_spawn_negative_effect_10`. Режим не ограничен. Доступны фильтры по `effect.type`, параметрам эффекта и всем полям enemy; unique по effect.type считает разные виды размещённых эффектов.

Бэк принимает явную модель `EnemyEffectPlacedData` с enemy, effect, mode; затем применяет общий механизм фильтров и счётчиков. Игровое поле он не меняет. В мультиплеере событие учитывается только у клиента, выполняющего размещение; получение состояния напарника не воспроизводит факт.

Это отдельное событие от `enemy.passive_triggered`: пассивка может запуститься, но не найти свободную клетку; тогда событие пассивки есть, а размещения — нет. Завещания тоже могут размещать эффекты без события пассивки.

## EnemyPassiveTriggered — запуск пассивки врага

Событие `enemy.passive_triggered` означает: таймер разрешил запуск и вызван поддерживаемый обработчик пассивки. Полезность результата не проверяется: лечение полностью здорового врага тоже считается. Пустое/неизвестное имя пассивки не создаёт событие.

### Откуда берутся данные

1. `enemy_passive_abilities_end_turn` собирает врагов с активными пассивками и живого лидера врагов.
2. `field_passives`, `deck_passives`, `grave_passives` проверяют `allowActionTimer`. При отказе до диспетчера выполнение не доходит.
3. Общий `run_passive` получает явную location и сохраняет копию всего enemy **до эффекта**, затем вызывает обработчик. После поддерживаемой ветки вызывает трекер с копией врага и location. Если обработчик планирует эффект через таймер, учитывается его запуск, а не завершение анимации.
4. Трекер добавляет mode через `resolveAchievementGameMode()` и кладёт независимый JSON-снимок в обычную очередь.

```json
{
  "type": "enemy.passive_triggered",
  "data": {
    "enemy": {
      "id": 7,
      "color": "Bronze",
      "faction": "Soldiers",
      "passive_ability": { "name": "heal-self" }
    },
    "location": "field",
    "mode": "normal"
  }
}
```

В примере enemy сокращён; реально передаётся полный объект. Зоны — `field`, `deck`, `grave`. Лидер врагов также проходит через field; чтобы учитывать только карты, нужен `enemy.color exists true`, только лидера — `exists false`.

### Подсчёт и контракты

Бэк принимает явную модель `EnemyPassiveTriggeredData`: enemy, mode, location, без наследования других Data-моделей. Дальше работают общие filters и counter: count для количества запусков, unique по enemy.id для разных видов врагов, фильтры по фракции/цвету/имени пассивки и вложенным параметрам. Отдельного подсчёта этого события в service нет.

Три примера контрактов в каталоге используют count, target 10 и соответствующую location. Режим намеренно не ограничен. Статистика `battleStats.enemy_passives_in_field` для условия победы остаётся отдельным счётчиком текущего боя: её увеличивает только field_passives после успешного диспетчера, без второго инкремента в трекере.

В мультиплеере событие получает клиент, который выполняет обработчик пассивки. Получение состояния от другого игрока не повторяет событие и не даёт обоим общий прогресс; синхронизация этих фактов не добавлялась.

Код: `src/logic/ai_move/passive_abilities/passives_{field,deck,grave,dispatcher}.ts`, `src/logic/achievements/trackAchievementEvent.ts`, `src/types/achievements.ts`; на бэке — `user_achievements/schemas.py` и общий `logic/events.py`.

## EnemyKilled — смерть врага или лидера врагов

### Как событие доходит до проверки контракта

**1. Игровая логика вызывает remove_dead_enemy.**

Единственное место создания EnemyKilled — функция `remove_dead_enemy` в `enemy_takes_damage.ts`. Обычный урон приходит сюда после проверки HP <= 0; также её вызывают обработчики яда/уничтожения и вражеская пассивка брони. Трекер не ищет причину смерти и не проверяет повторно здоровье: ему сообщает об этом обработчик смерти.

Обязательный третий аргумент remove_dead_enemy — hpBeforeDeath, четвёртый — timeout. При уроне сохраняем HP перед вычитанием damage и ставим проверку смерти только для смертельного удара. Перед удалением таймер всё ещё проверяет HP <= 0. Так таймер предыдущего несмертельного удара не подменит значение. Пример: 60 HP → удар 40 → удар 30 даёт hp_before_death = 20, а удар 100 по 60 HP даёт 60.

Повторный яд сохраняет HP в момент применения, до возможной задержки fromEffect. Пассивка превращения брони в здоровье при отсутствии брони передаёт HP непосредственно перед уничтожением. Поэтому поле работает и для прямого удаления без уменьшения HP уроном. Оно не является максимумом здоровья за бой; enemy.data.hp не подменяется.

Удаление случайного врага из колоды (`destroy_random_enemy_in_deck`), замена занятой клетки при перемещении (`move_enemy`) и замена своей картой (`place_self_in_field`) не создают EnemyKilled. Само исчезновение врага из игрового массива не считается этим событием.

**2. До изменения мёртвого врага вызываем мастер-функцию:**

```ts
trackAchievementEvent({
  type: AchievementEventType.EnemyKilled,
  enemy,
  hp_before_death: hpBeforeDeath,
})
```

Вызов стоит до очистки статуса, восстановления HP, перемещения в кладбище и выполнения завещания. Поэтому фильтры видят признаки врага именно в момент обработки смерти: например veil или наличие deathwish. Текущее HP может быть нулевым/отрицательным при смерти от урона; для контрактов на исходные жизни используем `enemy.data.base.base_hp`.

**3. Мастер-функция добавляет режим и копирует данные в очередь.**

Для EnemyKilled используется явная ветка:

```ts
eventData = {
  enemy: input.enemy,
  mode: resolveAchievementGameMode(),
  hp_before_death: input.hp_before_death,
}
```

Затем создаётся независимая JSON-копия, локальный UUID и вызывается `enqueueAchievementEvent`. Копирование происходит синхронно: дальнейшая очистка статуса или восстановление HP в remove_dead_enemy уже не меняют записанное событие.

**4. Фронт и бэк проверяют обычные filters и counter.**

На фронте `processAchievementEvents` использует enemy и mode напрямую. Дополнительной summary нет. Один враг может одновременно продвинуть контракты на общее число убийств, его цвет, фракцию и статус.

На бэке `EnemyKilledEvent` использует явную `EnemyKilledData`: полный `enemy: dict[str, JsonValue]`, обязательные mode и hp_before_death (конечное число). После проверки схемы `apply_events` передаёт словарь в общие фильтры и счётчики. Отдельной ветки подсчёта EnemyKilled нет. Бэк не убивает врага повторно и не проверяет состояние поля.

### Что отправляется и откуда берутся поля

| Поле | Источник |
|---|---|
| `enemy` | Полный аргумент enemy функции remove_dead_enemy, до очистки и восстановления |
| `hp_before_death` | HP до смертельного удара, повторного отравления или прямого уничтожения пассивкой брони |
| `mode` | Текущий игровой стор, который читает resolveAchievementGameMode() |

Пример запроса, enemy сокращён для чтения:

```json
{
  "events": [
    {
      "type": "enemy.killed",
      "data": {
        "enemy": {
          "id": 7,
          "color": "Bronze",
          "faction": "Soldiers",
          "deathwish": { "name": null, "description": null },
          "data": {
            "hp": 0,
            "damage": 7,
            "status": "veil",
            "base": { "base_hp": 7, "base_damage": 7 }
          }
        },
        "hp_before_death": 7,
        "mode": "normal"
      }
    }
  ]
}
```

Локальный ID события не отправляется. Если умер лидер врагов, enemy содержит полный объект лидера без color. Никакого отдельного события для него нет.

### Какие контракты можно описать

Для строк ниже event = `enemy.killed`, counter = count, target — нужное количество. Добавляем mode для ограничения режима. Фильтры соединяются через И.

| Контракт | filters |
|---|---|
| Убейте 50 обычных врагов | enemy.color exists true |
| Убейте 100 лидеров врагов | enemy.color exists false |
| Убейте врагов Soldiers | enemy.color exists true, enemy.faction = Soldiers |
| Убейте золотых врагов | enemy.color = Gold |
| Убейте врагов со статусом veil | enemy.color exists true, enemy.data.status = veil |
| Убейте врагов с завещанием | enemy.color exists true, enemy.deathwish.name ne null |
| Убейте врагов с базовыми жизнями больше 50 | enemy.color exists true, enemy.data.base.base_hp > 50 |
| Убейте врагов, у которых перед смертельным действием было хотя бы 50 HP | enemy.color exists true, hp_before_death >= 50 |

Без ограничения color контракт учитывает и обычных врагов, и лидеров. `deathwish.name ne null` требует существующего ненулевого имени; это не проверка того, что завещание уже выполнилось — событие создаётся перед ним.

Поддерживается и streak. Для «5 Bronze подряд, повторить 5 раз» используются length 5, target 5, основной фильтр enemy.color = Bronze и два reset по enemy.killed: другой существующий цвет (ne Bronze) либо отсутствие color (лидер). Условия режима нужно указать и в основном фильтре, и в reset. Уже завершённые серии сохраняются; неподходящие события и границы боёв сами по себе серию не сбрасывают.

Unique по enemy.id считает разные виды врагов, а не разные экземпляры одного вида. Две карты врага с одним id дают два факта для count, но одно уникальное значение для unique. Чтобы исключить пересечение ID карт и лидеров, такой контракт следует ограничить одним из этих видов через color.

### Отличие от кладбища при победе

EnemyKilled — факт обработки смерти. `GameWon.enemy_grave` — состав кладбища в конце боя. Это разные данные: лидер и враг со статусом Doomed не добавляются в обычное кладбище, но их смерть через remove_dead_enemy создаёт EnemyKilled. Поэтому для «убейте суммарно» используем EnemyKilled, а для «победите с минимум 30 врагами в кладбище» — GameWon.

Защиты от повторного вызова remove_dead_enemy в трекере нет: каждый вызов создаёт новый факт. enemy.id не используется для подавления повторов, потому что в бою могут быть разные экземпляры одного врага. В мультиплеере событие создаётся у клиента, который выполняет обработчик смерти; получение состояния напарника само по себе не воспроизводит событие.

## EnemyShieldRemoved и EnemyArmorRemoved — снятие защиты врага

### Как события доходят до проверки контракта

**1. Игровой обработчик сохраняет врага до изменения защиты.**

```ts
const before = copyObj(enemy)
// Здесь существующая игровая логика снимает щит или броню.
trackEnemyDefenceChanges(before, enemy)
```

`before` — независимый полный снимок. Второй аргумент — тот же игровой враг после эффекта. Общая функция не снимает защиту сама: она сравнивает два состояния и сообщает о результате.

**2. trackEnemyDefenceChanges определяет, что действительно снялось.**

- Щит: до эффекта data.shield был включён, после — выключен или отсутствует. Тогда создаётся EnemyShieldRemoved. Если щита и так не было, события нет.
- Броня: отсутствующее значение считается нулём; из неотрицательного значения до эффекта вычитается неотрицательное значение после. Если разница > 0, создаётся EnemyArmorRemoved с amount этой разницы. При неизменной/возросшей броне события нет; неконечные числа не учитываются.

Примеры брони: 5 → 4 даёт amount 1; 5 → 0 даёт amount 5; 2 → 0 после способности «снять 10» даёт amount 2. То есть считаем реально снятую броню, а не запрошенную силу способности.

Если эффект снял обе защиты, функция создаст два события: сначала щит, потом броню. Оба получают полный enemy из снимка before.

**3. Мастер-функция добавляет режим и кладёт события в очередь.**

Для щита:

```ts
trackAchievementEvent({
  type: AchievementEventType.EnemyShieldRemoved,
  enemy: before,
})
```

Для брони:

```ts
trackAchievementEvent({
  type: AchievementEventType.EnemyArmorRemoved,
  enemy: before,
  amount,
})
```

У каждого события своя явная ветка в мастере. Она добавляет mode через resolveAchievementGameMode(). Затем создаются независимая JSON-копия и локальный UUID, событие передаётся в enqueueAchievementEvent. Режим в игровых местах вызова передавать не нужно.

**4. Предварительный расчёт и бэк используют общие filters и counter.**

Дополнительных сводок и специальной обработки этих событий нет. На бэке EnemyShieldRemovedData явно содержит enemy и mode; EnemyArmorRemovedData явно содержит enemy, mode и amount. Обе модели наследуют только общий Base, поля одного события не спрятаны в другом. Enemy — произвольный JSON-объект; amount — положительное конечное число.

Бэк использует переданный факт и amount: не повторяет удар, не снимает защиту в игре и не вычисляет разницу состояний заново.

### Где подключено сравнение защиты

| Место | Что может быть засчитано |
|---|---|
| hit_one_enemy | Сначала щит; если его нет — 1 единица брони. После снятия защиты ветка возвращается, поэтому один такой удар не снимает сразу щит и броню. |
| lock_enemy | Щит, если блокировка прошла. При Veil функция выходит до эффекта и события. |
| purify | Щит. Снимок сделан до удаления статуса, пассивки и завещания, поэтому фильтры видят прежние признаки. Броню эта функция не снимает. |
| Пассивка remove_shield | Щит выбранного врага |
| remove_enemy_armor | Часть или вся броня одного врага |
| remove_all_enemies_armor | Отдельное событие снятия брони для каждого врага, у которого она уменьшилась |
| Эффект Fire в effects_interaction | Щит и вся броня; может создать оба события |

Случайное снятие/поглощение брони, делегирующее в remove_enemy_armor, учитывается там же; второй вызов трекера в обёртке не нужен. Самостоятельная потеря брони вражеской пассивкой lose_armor не подключена к этим событиям.

Причину снятия не передаём: удар, блокировка, очищение и огонь подходят под один тип события. Фильтры по «только ударом» здесь отсутствуют.

### Что отправляется на бэк

Пример: эффект снял щит и 3 единицы брони у одного врага. Enemy сокращён для чтения; в реальном запросе передаётся полный снимок до эффекта.

```json
{
  "events": [
    {
      "type": "enemy.shield_removed",
      "data": {
        "enemy": {
          "id": 7,
          "color": "Bronze",
          "faction": "Soldiers",
          "data": { "shield": true, "armor": 3 }
        },
        "mode": "normal"
      }
    },
    {
      "type": "enemy.armor_removed",
      "data": {
        "enemy": {
          "id": 7,
          "color": "Bronze",
          "faction": "Soldiers",
          "data": { "shield": true, "armor": 3 }
        },
        "mode": "normal",
        "amount": 3
      }
    }
  ]
}
```

enemy.data.armor — сколько брони было до эффекта, amount — сколько снялось. При снятии 1 из 3 эти значения будут 3 и 1 соответственно. У щита amount нет: его снятие — один факт. Локальные ID в запрос не входят.

### Какие контракты можно описать

| Контракт | event | counter | Дополнительные filters |
|---|---|---|---|
| Снимите щит 10 раз | enemy.shield_removed | count, target 10 | mode = normal, если нужен обычный режим |
| Снимите броню 10 раз | enemy.armor_removed | count, target 10 | Аналогично |
| Снимите суммарно 10 единиц брони | enemy.armor_removed | sum по amount, target 10 | Аналогично |
| Снимите не менее 5 брони с одного врага за одно изменение — 3 раза | enemy.armor_removed | count, target 3 | amount >= 5 |
| Снимите щиты у золотых врагов | enemy.shield_removed | count | enemy.color = Gold |
| Снимите броню у лидеров | enemy.armor_removed | count или sum amount | enemy.color exists false |

Если цвет не ограничен, подходят и враги-карты, и лидеры. Можно сочетать режим, фракцию, статус, завещание и другие поля снимка enemy обычными AND-фильтрами.

Одна способность, снявшая всю броню у трёх врагов с запасами 2, 3 и 5, создаёт три события: count увеличится на 3, sum amount — на 10. Это не «один раз примените способность». Повторное получение и снятие защиты с того же врага считается новым фактом; unique по enemy.id, если использовать такой счётчик, считает разные ID, а не экземпляры.

Старые контракты на снятие щита/брони менять не требуется: типы событий и поля запроса сохранились, mode присутствует у обоих.

## DeckCreated, DeckSaved и DeckDeleted — операции с колодами

### Чем отличаются создание и сохранение

**DeckCreated — появилась новая колода. DeckSaved — сохранён её состав.**

При создании произошло и то, и другое. При редактировании новая колода не появилась, но состав снова сохранён. Поэтому:

| Действие | События |
|---|---|
| Создать колоду | deck.created и затем deck.saved |
| Сохранить редактирование колоды | Только deck.saved |
| Удалить колоду | Только deck.deleted |
| Загрузить/просмотреть/выбрать колоду | Ни одного из этих трёх |

Так «создайте 5 колод» не выполняется пятью редактированиями одной колоды. А «соберите полностью бронзовую колоду» можно выполнить и сразу при создании, и изменив существующую.

### Как события доходят до проверки контрактов

**1. До запроса сохраняем данные колоды.**

В DeckbuildPage функция `achievementDeckSnapshot()` создаёт независимую JSON-копию:

```ts
{
  name: this.deck.deck_name.trim(),
  leader: this.deck.leader,
  cards: this.deck.deck_is_progress.map(entry => entry.card),
  health: this.deck.health,
}
```

Снимок нужен до await: успешный запрос сбрасывает форму сборки. Cards содержит полные объекты карт без обёрток, leader — полный объект лидера. Это данные формы, а не чтение колоды из уже очищенной формы после ответа.

При удалении DeckSelection сначала находит колоду по ID, сохраняет копию `selected.deck` и заменяет cards на список полных объектов карт. Здесь сохраняются также id и остальные поля выбранной колоды. После удаления записи в сторе уже не будет.

**2. После успешной операции вызываем мастер-функцию.**

- `DeckbuildPage.save_deck`: после createUserDeck — `{type: DeckCreated, data: {deck}}`.
- `DeckbuildPage.patch_deck`: после patchUserDeck — `{type: DeckSaved, data: {deck}}`.
- `DeckSelection.confirm_delete`: после deleteUserDeck — `{type: DeckDeleted, data: {deck}}`.

Если запрос завершился ошибкой, до вызова трекера выполнение не доходит. Для создания и редактирования сначала проходит существующая проверка формы.

**3. Мастер-функция кладёт готовое data в очередь.**

Общая ветка берёт `input.data`, делает независимую JSON-копию, добавляет локальный UUID и вызывает enqueueAchievementEvent. Режима mode у этих событий нет: работа с колодой не относится к конкретному бою.

После записи DeckCreated трекер сам вызывает себя ещё раз с DeckSaved и тем же снимком колоды. Компоненту не нужно отправлять оба события вручную. Это конечный вызов: у DeckSaved нет ветки, создающей ещё одно DeckSaved.

После создания и удаления дополнительно вызывается checkCurrentDecks для контрактов «имейте сейчас N колод». Это отдельная проверка: она ставит decks.checked с пустым data только при достижении цели current и отсутствии такого сигнала в очереди. Создание/удаление само по себе не означает обязательную отправку decks.checked. При редактировании число колод не меняется.

**4. Для DeckSaved вычисляем сводку состава.**

В processAchievementEvents фронт добавляет `deck.summary = buildDeckSummary(deck.cards)` к данным обработки. В событии очереди summary отсутствует. На бэке apply_events делает то же через build_deck_summary, используя проверенный `event.data.deck.cards`.

Сводка содержит cards_count, by_color.Bronze/Silver/Gold, neutral_count и флаги all_bronze/all_silver/all_gold/all_neutral/no_neutral — такие же, как для колоды в GameWon. Лидер в подсчёт карт не входит. Пустая колода не проходит условия «все карты такие-то».

У DeckCreated и DeckDeleted сводка автоматически не строится. Для проверки состава используем DeckSaved; для факта создания/удаления доступны исходные поля deck.

**5. Общие filters и counter считают прогресс.**

Бэк принимает все три типа через DeckEventData, в котором одно поле deck. UserDeckSnapshot явно перечисляет cards, leader, name и health; наследования от DeckComposition больше нет. Дополнительные поля колоды разрешены, чтобы сохранить id и другие сведения при удалении. Поля внутри карт и лидера остаются произвольным JSON для фильтров.

Далее — общая обработка заданий. События не создают, не редактируют и не удаляют колоду повторно: игровая операция уже выполнена соответствующей ручкой.

### Что отправляется на бэк

Пример создания. Поля карты и лидера сокращены для чтения, в запросе они полные:

```json
{
  "events": [
    {
      "type": "deck.created",
      "data": {
        "deck": {
          "name": "Бронзовая колода",
          "leader": { "id": 13, "faction": "Soldiers" },
          "cards": [{ "id": 1, "color": "Bronze", "faction": "Soldiers" }],
          "health": 100
        }
      }
    },
    {
      "type": "deck.saved",
      "data": {
        "deck": {
          "name": "Бронзовая колода",
          "leader": { "id": 13, "faction": "Soldiers" },
          "cards": [{ "id": 1, "color": "Bronze", "faction": "Soldiers" }],
          "health": 100
        }
      }
    }
  ]
}
```

Пример показывает два создаваемых события. Они не обязаны попасть в один HTTP-запрос: если первое довело контракт до цели, отправка может начаться до добавления второго.

После редактирования структура та же, но событие только deck.saved. При удалении — deck.deleted и снимок удалённой колоды, включая её id. При создании/редактировании текущий snapshot не содержит ID колоды, поэтому unique по deck.id для этих событий использовать нельзя. Локальные UUID и вычисленная summary в запрос не входят.

### Какие контракты можно описать

| Контракт | event | counter и filters |
|---|---|---|
| Создайте суммарно 5 колод | deck.created | count, target 5 |
| Создайте 5 колод за Soldiers | deck.created | count, target 5, deck.leader.faction = Soldiers |
| Удалите 3 колоды | deck.deleted | count, target 3 |
| Соберите полностью бронзовую колоду | deck.saved | count, target 1, deck.summary.all_bronze = true |
| Соберите полностью серебряную/золотую колоду | deck.saved | Аналогично all_silver/all_gold |
| Соберите колоду без нейтральных/только из нейтральных | deck.saved | Аналогично no_neutral/all_neutral |
| Соберите колоду из 20 карт | deck.saved | count, target 1, deck.summary.cards_count = 20 |
| Создайте колоды за три разные фракции | deck.created | unique по deck.leader.faction, target 3; при необходимости ограничить список фракций через in |

«Имейте 5 колод» — другой контракт: decks.checked, current по decks.count. Он учитывает текущее хранение, включая базовую колоду, а не число созданий за всё время.

DeckSaved означает факт сохранения, а не уникальную колоду и не доказанное изменение её состава. Если несколько раз успешно сохранить одну и ту же подходящую колоду, count увеличивается каждый раз, пока задание не завершено. Поэтому для «соберите бронзовую колоду» используется target 1; target 5 означал бы пять подходящих сохранений, а не пять разных колод.

## DecksChecked — сколько колод сейчас хранится у игрока

**DeckCreated считает создания за всё время. DecksChecked проверяет количество колод сейчас.** Например, создали пять колод, удалили четыре: число созданий осталось пять, а число хранящихся колод уменьшилось. Базовая колода тоже входит в хранение.

Это событие — просьба проверить состояние. Фронт не сообщает серверу ни количество, ни список колод: сервер сам читает их из БД.

### Как событие доходит до проверки контракта

**1. Фронт проверяет количество после загрузки, создания и удаления.**

При загрузке installAchievementSync ждёт три мутации: `set_decks`, `setUserAchievements` и `setAchievementsConfig`. Когда загружены колоды, прогресс и конфиги, один раз вызывает checkCurrentDecks. После входа/выхода из аккаунта флаги этой первичной проверки сбрасываются.

Ещё два места вызова — мастер-функция после DeckCreated и DeckDeleted. Операция с колодой к этому моменту уже успешно завершилась. Редактирование не меняет количество, поэтому после DeckSaved такой проверки нет.

**2. checkCurrentDecks сначала проверяет цель локально.**

Функция берёт `store.getters.all_decks.length` и передаёт его в previewCurrentDecks вместе с конфигами и подтверждённым прогрессом. Preview создаёт временное событие:

```ts
{
  id: "current-decks-preview",
  type: AchievementEventType.DecksChecked,
  data: { decks: { count } },
}
```

Оно нужно только для локального вызова processAchievementEvents: в очередь и HTTP-запрос этот объект не попадает. Общий обработчик проверяет filters и подставляет число колод в current-счётчик.

Если пользователь не авторизован, ни одна незавершённая цель не достигнута или в pendingEvents уже есть DecksChecked, новый сигнал не создаётся. Проверка наличия здесь относится именно к ожидающей очереди, не к уже отправленной пачке.

**3. При достижении цели отправляем пустой сигнал.**

```ts
trackAchievementEvent({
  type: AchievementEventType.DecksChecked,
  data: {},
})
```

Трекер использует общую ветку input.data и кладёт событие в очередь. installAchievementSync распознаёт DecksChecked и запускает отправку, не дожидаясь 10 секунд или 20 событий. Если другой запрос уже выполняется, новый сигнал остаётся в очереди до следующей отправки.

На бэк уходит:

```json
{
  "events": [
    { "type": "decks.checked", "data": {} }
  ]
}
```

Ни mode, ни deck, ни count в запросе нет. В схеме бэка DecksCheckedEvent использует пустую модель ResourcesCheckedData. Название общее с проверкой ресурсов, но полей ресурсов в этой модели нет: она запрещает любые дополнительные поля через extra="forbid".

**4. Бэк сам считает колоды пользователя.**

В AchievementsService.process_events есть отдельная ветка: если в пачке присутствует DecksChecked, сервис блокирует строку пользователя в users и считает строки user_decks для его user_id. Базовая колода учитывается наравне с остальными. Количество читается один раз для всей пачки.

Блокировка согласована с созданием/удалением колод: количество остаётся стабильным до завершения транзакции проверки и награждения. Получается серверный снимок `decks = {"count": число}`.

В apply_events пустое data заменяется на:

```json
{ "decks": { "count": 5 } }
```

Именно этот объект видят фильтры и счётчик на бэке. Клиентское число из preview здесь не используется.

**5. current заменяет прогресс текущим количеством.**

Для DecksChecked схема конфигов разрешает только counter.type = current и counter.field = decks.count. Это не прибавление единицы и не сумма проверок: value становится текущим количеством, ограниченным target.

Если цель достигнута, бэк обычным способом сохраняет выполнение и выдаёт награду. После подтверждения удаление колоды уже не отменяет выполненный контракт и награду.

### Что показывается на странице

Геттер localUserAchievements отдельно вызывает previewCurrentDecks с актуальным all_decks.length. Поэтому до подтверждения прогресс виден сразу и может уменьшаться: было 4/5, удалили колоду — стало 3/5. Для каждого такого изменения запрос не требуется; промежуточные числа в БД не обязаны совпадать с отображаемыми на странице.

Сервер подтверждает количество **на момент обработки**, а не исторический максимум. Если фронт увидел 5 колод, но до серверной проверки одну удалили, бэк увидит 4 и цель 5 не подтвердит. Если же награду уже выдали, контракт остаётся выполненным.

### Пример контракта

```json
"have_decks_5": {
  "id": "have_decks_5",
  "title": "Имейте в хранении 5 колод",
  "event": "decks.checked",
  "target": 5,
  "counter": { "type": "current", "field": "decks.count" },
  "filters": {},
  "rewards": { "resources": { "money": 1000 } },
  "ordering": 10
}
```

Для целей 3, 7 или 10 меняются id, title и target. Несколько таких контрактов проверяются одним событием. Состав и фракцию конкретной колоды проверяем через DeckSaved/DeckCreated: у DecksChecked есть только общее число колод, без их объектов.

## ResourcesChecked и UpgradesChecked — текущий баланс и прокачки

У этих событий общий принцип с DecksChecked: **фронт замечает достигнутую цель, а сервер проверяет её по своим данным**. Поэтому общий путь описан один раз, а источники данных — отдельно ниже.

ResourcesChecked отвечает на вопрос «сколько ресурсов есть сейчас», UpgradesChecked — «до чего сейчас прокачан пользователь». Получение денег за всё время считает ResourceGained, а количество покупок прокачек — UpgradePurchased. Загрузка состояния не является ни заработком, ни покупкой.

### Общий путь: локальная проверка → пустой сигнал → серверное подтверждение

**1. После загрузки вызываем проверку состояния.** Подписка installAchievementSync ждёт нужные мутации:

| Проверка | Что должно загрузиться |
|---|---|
| checkCurrentResources | set_resource, setUserAchievements, setAchievementsConfig |
| checkCurrentUpgrades | setUpgrades, setUserUpgrades, setUserAchievements, setAchievementsConfig |

Каждая первичная проверка выполняется один раз после готовности своей группы. При входе/выходе из аккаунта её флаг сбрасывается. Это позволяет подтвердить контракт, условие которого было выполнено ещё до появления самого контракта.

**2. Функция check сначала запускает локальный preview.** Для ресурсов она берёт getter resource; для прокачек — upgradesConfig и userUpgrades. Используется подтверждённый прогресс пользователя. Preview создаёт временное событие с данными и вызывает общий processAchievementEvents, не отправляя его в очередь.

Если пользователь не авторизован или ни одна незавершённая цель не достигнута, сигнала не будет. Если такой тип уже есть в pendingEvents, второй сигнал не добавляется. Проверка касается ожидающей очереди, не inFlightEvents. У checkCurrentResources также есть предварительный выход, если в каталоге вообще нет счётчиков current.

**3. При достижении цели мастер-функция получает только пустое data.** Например, если выполнены цели обоих типов, в запросе могут быть:

```json
{
  "events": [
    { "type": "resources.checked", "data": {} },
    { "type": "upgrades.checked", "data": {} }
  ]
}
```

Это два независимых сигнала; они не обязаны отправляться вместе. Баланса, уровней и mode в запросе нет. На фронте используется обычная ветка input.data в трекере. Синхронизация запускает отправку сразу, без ожидания таймера или заполнения очереди; выполняющийся запрос сначала должен закончиться.

На бэке оба события используют ResourcesCheckedData: пустую модель с extra="forbid". Она запрещает передавать произвольные поля вместо пустого объекта. UpgradesCheckedEvent не наследуется от события ресурсов — лишь использует ту же модель пустого data.

**4. Бэк получает состояние из БД и подставляет его в обработчик.** Снимки читаются только для присутствующих в пачке checked-событий, один раз на тип за пачку. Затем apply_events заменяет пустое data серверным снимком. Все фильтры и current-счётчики читают уже его.

**5. current заменяет value текущим числом, ограниченным target.** Он не прибавляет число при каждой проверке. Если цель достигнута, прогресс и награда сохраняются в общей транзакции. Подтверждённое выполнение впоследствии не отменяется.

Геттер localUserAchievements вызывает оба preview и для отображения страницы. Поэтому промежуточный прогресс виден без запроса на каждое изменение. Preview не ставит даты выполнения и не выдаёт наград.

### ResourcesChecked: откуда берётся баланс

**На фронте** previewCurrentResources создаёт временные данные:

```ts
data: { resources: store.getters.resource }
```

Помимо первичной загрузки, checkCurrentResources вызывается централизованно после обработки следующих входов мастер-функции:

- ResourcesChanged — обычное изменение ресурсов;
- ResourceGained в форме before/after — получение награды по разнице балансов;
- ResourceTransition — покупка, продажа, крафт или разбор ресурса;
- ActorTransition — крафт или разбор карты/лидера;
- UpgradeChanged — покупка прокачки.

Эти вызовы используют уже обновлённый баланс стора. Прямая отправка готового ResourceGained с resources сама по себе не вызывает checkCurrentResources. Обычная мутация set_resource также не означает постоянную автоматическую проверку: подписка использует её для готовности первой загрузки.

Отдельное место — sendAchievementEvents в сторе достижений. Если ответ содержит user_resources, сначала сохраняется подтверждённый прогресс, затем новый баланс, учитываются фактически выданные награды как доход и вызывается checkCurrentResources. Поэтому награда одного контракта может довести до цели другой контракт на накопление.

**На бэке** AchievementsService блокирует строку user_resources и читает баланс через get_user_resources. Это фактический остаток, после игровых начислений, расходов и лимитов. В apply_events получается, например:

```json
{ "resources": { "money": 20000, "silk": 15 } }
```

Здесь для краткости показаны два ресурса; снимок содержит полный баланс. Поле счётчика — resources.<имя ресурса>, например resources.money. Схема конфига проверяет имя по ResourceType.

Для «накопите хотя бы 100 камней одного из видов» используется максимум, а не сумма:

```json
"counter": {
  "type": "current",
  "fields": ["resources.raw_bronze", "resources.raw_silver", "resources.raw_gold"],
  "aggregation": "max"
},
"target": 100
```

Баланс 30/40/30 даёт 40/100, а 100/0/0 выполняет контракт. Это максимум среди ресурсов сейчас, не исторический максимум. Fields должен быть непустым; одновременно указывать field нельзя. Этот вариант разрешён только для resources.checked. Если хоть одно поле отсутствует, отрицательно или не является конечным числом, проверка пропускается. При загрузке и после изменения баланса используется тот же существующий путь проверки; новых вызовов в компонентах не требуется.

Снимок читается **до наград этой пачки**. Внутри apply_events награды ещё не увеличивают баланс для текущей проверки. Их влияние проверится отдельным сигналом после ответа на фронт.

Пример: при цели 20000 было 19000, получили фактически 1000 — preview показывает 20000/20000 и отправляет сигнал. Если до обработки успели потратить 500, сервер увидит 19500 и цель не подтвердит. Это проверка текущего остатка, а не максимума за историю. После подтверждения тратить деньги можно: выполненный контракт сохраняется.

### UpgradesChecked: как получаются уровень, значение и максимум

**На фронте** previewCurrentUpgrades вызывает buildUpgradeSnapshot(upgradesConfig, userUpgrades). **На бэке** сервис блокирует строку user_upgrades, читает её data и вызывает build_upgrade_snapshot с конфигом game_constants.upgrades. Алгоритм сборки один и тот же по смыслу; клиентский снимок на бэк не передаётся.

Кроме первичной загрузки, checkCurrentUpgrades вызывается после UpgradeChanged. До неё покупка уже завершилась, а стор получил новые уровни. Прямое событие UpgradePurchased само по себе эту проверку не запускает.

Снимок имеет два верхних ключа: upgrades и summary. Например, отдельный параметр может выглядеть так:

```json
{
  "upgrades": {
    "game": {
      "max_cards_in_deck": { "level": 2, "value": 12, "maxed": false }
    }
  }
}
```

Числа здесь иллюстративные. level — сохранённый номер ступени пользователя; value — эффект этой ступени из конфига. Для «достигните размера колоды 12» нужен value, а не level. maxed означает, что у текущей ступени next явно равен null.

Сборщик обходит разделы resources, settings, game и inventory из UpgradeType. Если у пользователя нет записи параметра, берёт уровень 0. Если ступень не найдена в конфиге, параметр не получает выдуманного значения и не считается максимальным, но остаётся в общем количестве прокачек.

Для каждого upgrade type, а также для групп all и non_settings формируется summary:

| Поле | Что означает |
|---|---|
| total_count | Сколько параметров прокачки есть в этой группе |
| maxed_count | Сколько параметров достигли максимума |
| all_maxed | Число 1, если группа непустая и все параметры максимальны; иначе 0 |

all включает settings; non_settings исключает этот раздел. Сводки разделов находятся, например, в summary.inventory и summary.settings. Это параметры прокачек пользователя, не покупки внутри аренного забега.

Почему all_maxed — 0/1, а maxed — boolean? Фильтр может проверять boolean, но current читает число. Поэтому «всё на максимум» удобно задавать счётчиком по summary.all.all_maxed с target 1.

Схема конфигов разрешает для UpgradesChecked поля upgrades.<upgrade_type>.<upgrade_subtype>.level/value и summary.<группа>.total_count/maxed_count/all_maxed. maxed можно использовать в filters, но не как поле current-счётчика.

Цель должна быть достижима по актуальному конфигу прокачек. Список параметров для «всё» также берётся из текущего конфига: добавление параметра меняет условие ещё не выполненного контракта, но не отменяет уже подтверждённое выполнение.

### Какие контракты описываются

У всех строк counter.type = current. Бэк требует именно этот тип для checked-событий.

| Контракт | event | counter.field | target |
|---|---|---|---|
| Накопите 20000 денег | resources.checked | resources.money | 20000 |
| Накопите 15 silk | resources.checked | resources.silk | 15 |
| Достигните размера колоды 12 | upgrades.checked | upgrades.game.max_cards_in_deck.value | 12 |
| Достигните второго уровня этой прокачки | upgrades.checked | upgrades.game.max_cards_in_deck.level | 2 |
| Прокачайте любой параметр, кроме settings, до максимума | upgrades.checked | summary.non_settings.maxed_count | 1 |
| Прокачайте все параметры до максимума | upgrades.checked | summary.all.all_maxed | 1 |
| Прокачайте весь inventory до максимума | upgrades.checked | summary.inventory.all_maxed | 1 |
| Прокачайте весь settings до максимума | upgrades.checked | summary.settings.all_maxed | 1 |

Для накопления значение может уменьшаться до подтверждения, а завершённые контракты остаются выполненными. Несколько целей по одному ресурсу или прокачкам проверяются одним сигналом своего типа.

## ResourceSpent и ResourceGained — расходы и доходы за всё время

**Эти события сообщают об уже выполненной операции. Они не списывают и не начисляют указанные в них ресурсы повторно.** Бэк использует суммы только для прогресса контрактов; отдельно он может выдать награду за выполненный контракт.

В обоих событиях data.resources — словарь положительных количеств. Знак определяется типом события:

```json
{
  "events": [
    { "type": "resource.spent", "data": { "resources": { "money": 300, "keys": 1 } } },
    { "type": "resource.gained", "data": { "resources": { "flowers": 1 } } }
  ]
}
```

Это пример формата, а не конкретного игрового рецепта. Одно событие содержит все ресурсы своего направления, а не отдельное событие на каждый ресурс. Нулевые изменения и пустые словари нормализатор не отправляет.

### От вызова на странице до готовых событий

**1. Сначала выполняется игровая операция.** Компонент сохраняет баланс before до await, вызывает существующий экшен изменения ресурсов, затем передаёт трекеру результат и баланс after. Вызов расположен после успешной операции; сами processResources и мутации ресурсов трекер не вызывают.

Основной локальный вход выглядит так:

```ts
trackAchievementEvent({
  type: AchievementEventType.ResourcesChanged,
  data: { resources: { money: -300, flowers: 1 }, before, after },
})
```

ResourcesChanged — промежуточный тип только для фронта. В запросе его не будет: мастер-функция преобразует его в ResourceSpent и/или ResourceGained.

**2. getResourceChanges разделяет изменения на spent и gained.**

- Если передан resources, отрицательные числа становятся положительными расходами. Для расхода берётся переданное количество: повторной проверки лимита или обрезания по before/after нет.
- Для положительных чисел нужны оба баланса. Доход равен меньшему из запрошенного количества и положительной разницы after − before. Без обоих значений доход из этого входа не записывается.
- Если resources не передан, изменения вычисляются как after − before по полям, присутствующим с конечными числами в обоих снимках. Минусы становятся расходами, плюсы — доходами.
- Нули и неконечные числа игнорируются.

Например, обещано +1000 денег, но баланс изменился с 4900 до 5000: в ResourceGained будет money: 100. Следующая награда при 5000 → 5000 не создаст доходного события. Сравнение балансов предполагает последовательную операцию: постороннее изменение между before и after может повлиять на разницу.

**3. trackResourceChanges создаёт готовые события.** Сначала ResourceSpent, затем ResourceGained, если соответствующие словари непустые. Готовые data проходят общую ветку трекера: независимая JSON-копия, локальный UUID, очередь. Mode автоматически не добавляется.

**4. Проверяется текущее накопление.** После ResourcesChanged вызывается checkCurrentResources. Доход за всё время и текущий остаток — разные контракты: первый двигает ResourceGained, второй подтверждается отдельным ResourcesChecked.

### Другие входы и источники

Тот же расчёт расходов/доходов вызывают ResourceTransition (обмен ресурса), ActorTransition (крафт/разбор карты или лидера) и UpgradeChanged (покупка прокачки). Их подробности не нужно повторять в компонентах.

ResourceGained имеет ещё две формы вызова:

- `{ before, after }` — локальная форма для награды, когда известны только балансы. Берёт положительные разницы, а уменьшения игнорирует; затем проверяет current. Так подключён WinPage.open_levels.
- `{ resources }` — уже известный фактический доход. Он сразу попадает в очередь без пересчёта и проверки лимита. Так trackAchievementRewards передаёт положительные суммы из granted_rewards; проверку current после ответа отдельно вызывает стор достижений.

Основные места подключения:

| Место | Что учитывается |
|---|---|
| StartGame, ArenaStartGame, LevelPage | Плата за уровень или вход на арену |
| WinPage.pay_resources, ArenaWinPage | Фактические ресурсы за победу |
| WinPage.open_levels | Ресурсы за открытие связанных уровней/завершение сезона |
| BonusPage.pay_resource | Списание открываемого предмета, получение выбранной награды ключа |
| BonusPage.handleAction | Расходы и доходы обмена ресурса |
| CardModal | Расходы/доходы крафта и разбора через ActorTransition |
| UpgradesPage | Расходы/доходы покупки через UpgradeChanged |
| useInventory вне арены | Списание использованного предмета |
| Стор достижений | Фактически выданные награды контрактов |

Необязательный subtype — причина операции, если её передал вызывающий код. Не нужно путать её с type события. При использовании обычного инвентаря передаются subtype: use_inventory_item и item: название предмета; item переносится только в расход. Например, unique по item позволяет считать разные использованные предметы. BonusPage.pay_resource передаёт subtype игровой ручке, но в текущем вызове трекера его не передаёт — в этих событиях фильтровать по нему нельзя.

### Что делает бэк и какие контракты доступны

ResourceSpentEvent и ResourceGainedEvent используют одну ResourceAmountsData. Все поля перечислены прямо в ней: resources, необязательные subtype и item. Скрытого наследования полей между моделями событий нет. Ключи resources проверяются по ResourceType, количества — как положительные конечные числа. item, если задан, тоже проверяется по ResourceType.

В apply_events нет отдельной ветки расчёта этих расходов/доходов: берётся data события, применяются общие filters и counter. Бэк достижений не восстанавливает операцию и не проверяет расход по истории баланса. Фактические суммы здесь сообщает фронт после игрового запроса.

| Контракт | event | counter / filters |
|---|---|---|
| Потратьте суммарно 10000 денег | resource.spent | sum, field resources.money, target 10000 |
| Заработайте суммарно 3000 scraps | resource.gained | sum, field resources.scraps, target 3000 |
| Потратьте деньги в пяти операциях | resource.spent | count, target 5; resources.money gt 0 |
| Используйте каждый предмет обычного инвентаря | resource.spent | unique по item; subtype = use_inventory_item; item in со списком предметов; target — длина списка |

Для sum по resources.money отдельный фильтр имени ресурса не требуется: если поля нет, событие не увеличит сумму. Count считает события, а не количество единиц ресурса.

## ResourceTransformed — покупка, продажа, крафт или разбор ресурса

Это отдельный факт операции, дополняющий её обычные ResourceSpent/ResourceGained. Он нужен, чтобы связать стоимость с действием и предметом: например, купить именно crops/wood/silk на сумму 10000 денег.

### Как формируется событие

**1. BonusPage.handleAction сохраняет параметры до запроса.** resource — название выбранного ресурса, action — buy/sell/craft/mill, quantity — количество операций, recipe — копия рецепта одной операции, step — количество единиц ресурса за одну операцию из resources_config. Before сохраняется до processResources, after берётся после успешного ответа.

В мастер-функцию передаётся локальный ResourceTransition с этими полями. Он не отправляется на бэк достижений напрямую.

**2. trackResourceTransition рассчитывает количества.** Проверяет положительный конечный step, положительный целый quantity и известный action. Amount = quantity × step. Для buy/craft сам ресурс прибавляется, для sell/mill — убывает. Рецепт дополняется этим изменением, затем все значения умножаются на quantity.

Например, десять покупок по 100 scraps дают amount: 1000. Это не 10 и не один клик. Amount повторно не ограничивается по балансу: допустимое количество обмена проверяется игровым интерфейсом/операцией. Расход и доход рассчитываются общим getResourceChanges, включая ограничение дохода фактической разницей баланса.

**3. Создаются обычные расход/доход, затем ResourceTransformed и проверка current.** В самом ResourceTransformed лежат:

```json
{
  "type": "resource.transformed",
  "data": {
    "action": "buy",
    "resource": "flowers",
    "amount": 1,
    "recipe": { "money": -300 },
    "spent": { "money": 300 },
    "gained": { "flowers": 1 }
  }
}
```

Пример иллюстративный. Spent/gained — положительные количества; словарь может быть пустым. Recipe — исходный рецепт одной операции со знаками, без умножения на quantity и без добавления изменения самого resource. Quantity, step и снимки баланса в это событие не входят. Режима и категории ресурса здесь тоже нет: принадлежность к инвентарю или материалам уровня задаётся фильтром resource in со списком имён.

### Бэк и контракты

ResourceTransformedData напрямую содержит action, resource, amount, recipe, spent и gained. Action ограничен четырьмя действиями, resource и ключи словарей — ResourceType, количества — положительные числа; recipe содержит конечные числа со знаками. Наследования, скрывающего эти поля, нет.

`unique` по `recipe` считает разные составы/количества в рецепте. Количество операций не меняет рецепт. Одинаковые рецепты у разных предметов считаются одним; action и resource сами по себе не входят в уникальность. Ограничение действия (например только craft) задаётся filters. В ActorTransformed рецепт уже передавался, и там этот же механизм также работает. Сохранённые контракты на уникальные ID/имена менять не требуется.

Бэк применяет обычные фильтры и счётчики. Он не выполняет обмен повторно и не пересчитывает рецепт. Расходы в ResourceTransformed не удваивают ResourceSpent: у задания один основной event, и оно читает только подходящий тип.

| Контракт | counter | filters |
|---|---|---|
| Скрафтите 10 бочек обоих видов | sum amount, target 10 | action = craft; resource in [kegs, big_kegs] |
| Купите 3000 flowers | sum amount, target 3000 | action = buy; resource = flowers |
| Купите материалы уровня на 10000 денег | sum spent.money, target 10000 | action = buy; resource in [crops, wood, silk] |
| Продайте предметов на 30000 денег | sum gained.money, target 30000 | action = sell |
| Потратьте 50000 денег одной покупкой или крафтом | count, target 1 | action in [buy, craft]; spent.money gte 50000 |
| Создайте каждый предмет инвентаря | unique resource | action = craft; resource in со списком предметов; target — длина списка |

Count здесь считает успешные вызовы обмена. Для количества предметов нужен sum amount: один массовый обмен может содержать много единиц.

## ResourceOpened — открытие ключа, бочки или сундука

Это **факт открытия одного предмета**, отдельно от его списания и получения награды.

**1. BonusPage.openResource выбирает обработчик:** open_keg, open_big_keg, open_chest или open_key. Каждый сначала проверяет наличие предмета, списывает одну единицу через pay_resource, подготавливает варианты награды и открывает окно. После этого возвращает true. Если предмета нет, возвращает false; при ошибке await до события выполнение не доходит.

**2. Только при true openResource вызывает трекер:**

```ts
trackAchievementEvent({
  type: AchievementEventType.ResourceOpened,
  data: { resource: resource_name },
})
```

**3. Общая ветка трекера отправляет эти данные без дополнительных полей:**

```json
{ "type": "resource.opened", "data": { "resource": "keys" } }
```

Ключ считается открытым, когда показан выбор награды, а не когда игрок принял один из вариантов. Принятие награды позже вызывает отдельное изменение ресурсов. Само списание ключа уже создало ResourceSpent через pay_resource; ResourceOpened его повторно не создаёт.

На бэке ResourceOpenedData прямо объявляет одно поле resource: ResourceType. Отдельного обработчика открытия в apply_events нет: работают общие фильтры и счётчик. Схема допускает имя из ResourceType, а текущий фронтовый источник создаёт события только для keys/kegs/big_kegs/chests.

| Контракт | counter | filters |
|---|---|---|
| Откройте 10 ключей | count, target 10 | resource = keys |
| Откройте суммарно 10 бочек обоих видов | count, target 10 | resource in [kegs, big_kegs] |
| Откройте суммарно 10 любых из четырёх предметов | count, target 10 | resource in [keys, kegs, big_kegs, chests] |
| Откройте каждый из четырёх видов | unique resource, target 4 | resource in [keys, kegs, big_kegs, chests] |

Amount здесь отсутствует: каждый успешный вызов означает одно открытие.

## InventoryUsed — применение предмета в бою

Событие сообщает об одном применении предмета, включая аренный инвентарь. Оно отличается от ResourceSpent: расход описывает списание из обычного запаса, а InventoryUsed — применение и измеренный результат эффекта.

### Как формируются данные

В [useInventory.ts](../../src/mixins/GamePage/useInventory.ts) после проверок возможности применения сохраняется mode через resolveAchievementGameMode(). Это происходит до await и эффекта: предмет может завершить бой, поэтому режим берём заранее.

В обычном бою сначала выполняется processResources со списанием одного предмета. Этот расход отдельно отправляется через трекер. В арене вместо списания общего ресурса вызывается мутация arena_use_inventory_item, уменьшающая запас предмета текущего забега.

Затем выполняется эффект предмета. После ветки эффекта отправляется InventoryUsed с item, сохранённым mode и result. При ошибке до этой точки событие не создаётся. Обработчик после отправки продолжает обычное завершение применения предмета.

Для draw_cards результат измеряется разницей размера руки до и после появления карт. Желаемое количество берётся из прокачки и ограничивается свободным местом, но в контракт отправляется именно фактическая разница. Поэтому при прокачке на три карты и двух свободных местах result.cards_drawn будет 2.

```json
{
  "type": "inventory.used",
  "data": {
    "item": "draw_cards",
    "mode": "normal",
    "result": { "cards_drawn": 3 }
  }
}
```

Для остальных предметов result сейчас пустой: `{}`. Это означает факт применения, без числовой оценки пользы эффекта. Трекер не вычисляет result дополнительно и не добавляет mode: оба поля уже передал игровой обработчик. При нулевом фактическом доборе cards_drawn равен 0, а не отсутствует.

### Бэк и контракты

InventoryUsedData явно перечисляет mode, item и result. Item проверяется по ResourceType; значения result — целые неотрицательные числа. Бэк применяет общие filters/counter и не воспроизводит эффект предмета.

| Контракт | counter | filters |
|---|---|---|
| Используйте суммарно 5 любых предметов | count, target 5 | Без фильтров — все переданные режимы |
| Используйте mega_bombs 3 раза | count, target 3 | item = mega_bombs |
| Используйте 10 предметов в арене | count, target 10 | mode = arena |
| Возьмите draw_cards ровно 3 карты за применение, 5 раз | count, target 5 | item = draw_cards; result.cards_drawn = 3 |
| Возьмите предметом суммарно 30 карт | sum result.cards_drawn, target 30 | item = draw_cards |
| Используйте каждый предмет из списка | unique item | item in со списком; target — число разных предметов |

Фильтр режима добавляется по желаемому охвату. Старые контракты по resource.spent/use_inventory_item сохраняют другой смысл: они учитывают расход обычного запаса и не получают аренные применения.

## InventoryRestored — восстановление аренного предмета

Источник — restore_inventory в [ArenaDeckbuildPage.vue](../../src/pages/ArenaDeckbuildPage.vue). Сначала can_restore_inventory проверяет фазу ready, наличие прокачки ARENA_RESTORE_SLOT, доступность слота, выбранный предмет и нулевой остаток предмета. Затем мутация arena_restore_inventory_slot восстанавливает слот, и трекер получает:

```json
{
  "type": "inventory.restored",
  "data": { "item": "mega_bombs", "mode": "arena" }
}
```

Item берётся из выбранного слота до мутации, mode указан явно как arena. Номер слота и количество восстановленных единиц не передаются. Покупка самой прокачки восстановления не создаёт это событие: оно возникает именно по кнопке восстановления.

InventoryRestoredData на бэке прямо содержит mode и item. Обработка общая: count считает восстановления, unique по item — разные восстановленные предметы. Для «восстановите инвентарь 10 раз в арене» подходят count/target 10 и mode = arena; для конкретного предмета добавляется фильтр item. Сам бэк достижений слот повторно не восстанавливает.

## ActorTransformed — крафт и разбор карты или лидера

Это событие относится к объектам коллекции, а не к ресурсам из BonusPage. Источники — confirm_craft и confirm_mill в [CardModal.vue](../../src/components/ModalWindows/CardModal.vue).

### Откуда берутся поля

До запроса сохраняются полная копия actor из user_card.card, копия выбранного recipe и баланс before. После успешного processCraftMillCard берётся возвращённый баланс after. Снимок actor нужен заранее: после разбора объект может исчезнуть из коллекции.

Трекер сначала определяет обычные расходы/доходы по разнице балансов. Затем создаёт ActorTransformed:

```json
{
  "type": "actor.transformed",
  "data": {
    "action": "craft",
    "actor": { "id": 7, "color": "Gold", "faction": "Soldiers" },
    "recipe": { "rare_gem": -1 },
    "spent": { "rare_gem": 1 },
    "gained": {}
  }
}
```

Actor в примере сокращён, рецепт иллюстративный. В реальном событии actor полный, recipe сохраняет исходные знаки. Spent/gained содержат положительные фактические разницы; до/после и mode в запросе отсутствуют. После постановки событий дополнительно проверяется текущий баланс.

ActorTransformedData на бэке прямо перечисляет action (craft/mill), actor, recipe, spent и gained. Внутри actor допускается вложенный JSON для фильтров. Бэк не крафтит и не разбирает объект повторно, не пересчитывает рецепт: применяется общий механизм контрактов.

### Какие контракты доступны

Одна операция — один объект, поэтому количество крафтов/разборов считается count. Отдельного amount в событии нет.

| Контракт | counter | filters |
|---|---|---|
| Создайте суммарно 100 карт | count, target 100 | action = craft; actor.color exists true |
| Создайте суммарно 5 лидеров | count, target 5 | action = craft; actor.color exists false |
| Разберите 100 карт / 3 лидеров | count с нужной целью | action = mill; проверка наличия color |
| Создайте 100 карт Soldiers | count, target 100 | action = craft; actor.color exists true; actor.faction = Soldiers |
| Создайте лидера каждой нужной фракции | unique actor.faction | action = craft; actor.color exists false; actor.faction in со списком; target — длина списка |
| Создайте объект с расходом rare_gem | count, target 1 | action = craft; spent.rare_gem gt 0 |

Фильтр по recipe.rare_gem также доступен: например, ne 0 проверяет ненулевое поле исходного рецепта, независимо от знака. Отсутствующее поле не проходит ne. Для именно фактического расхода используем spent.rare_gem; для особенностей выбранного рецепта — recipe.

Полный actor позволяет сочетать любые поддерживаемые проверки его полей: цвет, фракцию, способность, базовые характеристики. Одно событие может продвинуть несколько подходящих контрактов.

## UpgradePurchased — покупка обычной прокачки

Источник — handleUpgrade в [UpgradesPage.vue](../../src/pages/UpgradesPage.vue). После успешного postUserUpgrade страница передаёт выбранные upgrade_type/upgrade_subtype и новые уровни из ответа в трекер. Тот собирает снимок прокачек и извлекает купленный параметр.

Если параметр найден, создаётся событие:

```json
{
  "type": "upgrade.purchased",
  "data": {
    "upgrade_type": "game",
    "upgrade_subtype": "max_cards_in_deck",
    "level": 2,
    "value": 12,
    "maxed": false
  }
}
```

Числа иллюстративные. Level — номер достигнутой ступени из ответа бэка. Value — эффект этой ступени из конфига. Maxed — у ступени next равен null. При неизвестной ступени факт покупки не создаётся с выдуманными полями; учёт ресурсов и проверки состояния выполняются независимо.

Расход/доход операции учитывается отдельно, после чего вызываются проверки текущего баланса и прокачек. В самом UpgradePurchased нет стоимости, полного набора прокачек и mode.

На бэке UpgradePurchasedData прямо перечисляет все пять полей. Type/subtype проверяются по enum прокачек, level — положительное целое, value — число или boolean, maxed — boolean. Обработчик достижений использует присланный факт и обычные filters/counter; он не покупает прокачку и не достраивает снимок из БД для этого события.

| Контракт | counter | filters |
|---|---|---|
| Совершите 10 любых прокачек | count, target 10 | Без фильтров |
| Совершите 5 прокачек inventory | count, target 5 | upgrade_type = inventory |
| Купите ступень, достигнув максимума | count, target 1 | maxed = true; при необходимости upgrade_type ne settings |
| Купите прокачки трёх разных типов | unique upgrade_type, target 3 | При необходимости ограничить типы через in |

Отличие от UpgradesChecked: UpgradePurchased считает новую покупку. Для «уже иметь параметр на максимуме», «все прокачки на максимум» и проверки при загрузке используем UpgradesChecked. Он подтверждает состояние по БД даже без новой покупки.

## ArenaUpgradePurchased — покупка прокачки внутри арены

Источник — doUpgrade в [ArenaUpgradesModal.vue](../../src/components/Pages/ArenaDeckbuildPage/ArenaUpgradesModal.vue). Если у текущей ступени есть next, выполняется оплата через processResources. После успешной оплаты arena_increment_upgrade увеличивает уровень, а трекер получает подтип и **новый** уровень:

```json
{
  "type": "arena.upgrade.purchased",
  "data": { "upgrade_subtype": "arena_restore_slot", "level": 1 }
}
```

Level берётся из userLevel(key) уже после мутации. Затем отдельно синхронизируются игровые параметры арены. Событие не содержит upgrade_type, value, maxed, стоимости или mode: принадлежность к арене задана самим типом события.

ArenaUpgradePurchasedData прямо содержит upgrade_subtype: UpgradeSubtype и положительный целый level. Бэк достижений обрабатывает присланный факт общими счётчиками, не покупает прокачку и не увеличивает её уровень повторно.

«Купите суммарно 10 прокачек в арене» — count/target 10. Для конкретной прокачки добавляется upgrade_subtype. Для «купите эту прокачку до третьего уровня» можно использовать count/target 1 с фильтрами upgrade_subtype и level gte 3: это условие покупки, не проверка сохранённого состояния при загрузке. Unique по upgrade_subtype считает разные купленные виды прокачек.

## ArenaLevelReached — достигнутый номер уровня арены

Источник — created в [ArenaWinPage.vue](../../src/pages/ArenaWinPage.vue). Страница проверяет и сбрасывает одноразовый win_redirect, отправляет GameWon и запоминает номер завершённого уровня. Затем arena_advance_level повышает current_level, и отправляется его **новое** значение:

```json
{ "type": "arena.level.reached", "data": { "level": 5 } }
```

Это означает: после победы над четвёртым уровнем игрок дошёл до пятого. Это не победа над пятым уровнем. Для таблицы лидеров рядом используется completed_level — прежний номер; не нужно путать эти два значения.

Событие ставится в очередь после продвижения арены, до ожидания завершения запросов таблицы лидеров и награды. Повторное открытие страницы без win_redirect не создаёт его снова. Вход в новый забег сам по себе этого события не создаёт.

ArenaLevelReachedData на бэке содержит только положительное целое level. В apply_events нет особого механизма максимума: нужный порог задаётся обычным фильтром.

| Контракт | counter | filters |
|---|---|---|
| Дойдите до пятого уровня арены | count, target 1 | level gte 5 |
| Дойдите до десятого уровня арены | count, target 1 | level gte 10 |
| Дойдите до двадцатого уровня арены | count, target 1 | level gte 20 |

Здесь target — число подходящих событий, не номер уровня. Поэтому target 5 с level gte 5 не означает «пять забегов до пятого»: переходы на 5, 6, 7, 8 и 9 в одном забеге тоже подходят. Для подсчёта достижений ровно пятого уровня используется level = 5; идентификатора забега в событии нет.

### Общая обработка последних шести событий на бэке

Все шесть принимаются типизированными Event/Data-моделями в `services/api/app/apps/user_achievements/schemas.py`. Поля данных объявлены прямо в своих классах, включая mode у InventoryUsedData и InventoryRestoredData. Общего родителя GameModeData больше нет.

В `logic/events.py` для них нет специальных преобразований data: выбор заданий по event, проверка filters и общий counter. Прогресс и награды сохраняются через `service.py`. Схемы проверяют формат события, но обработчик достижений не повторяет игровую операцию и не восстанавливает её историю из БД.
